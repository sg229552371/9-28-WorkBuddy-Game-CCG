## 一、诊断结论（代码证据，非猜测）

### 1.1 寻路卡障碍 —— 根因：无全局寻路，纯局部贪心

现状：全游戏**没有任何寻路算法**。怪、队友、Boss 的移动都是「直线朝目标走 + 逐障碍推挤」，防卡死全靠 `resolveObstacles`（HTLM/js/game.js:1452）里的**切向滑动**：

```
推挤：把实体沿法向推出障碍 → 只恢复间隙，不产生切向运动
切向滑动：正对顶墙时沿墙面向目标一侧滑（带 _slideDir 粘性防振荡）
```

为什么卡：
- **凹形障碍死锁**（局部极小值）：L 形、U 形、两障碍夹缝时，切向绕行在凹角处来回打转，永远出不去。切向滑动是局部贪心——它能绕过「一面墙」，绕不出「一个口袋」。
- **O(怪×障碍) 全量遍历**：每怪每帧遍历 `w.obstacles` 全量，3000 怪性能主线下这本身就是隐患。
- **无卡死检测**：怪卡死时没有任何兜底逻辑发现它。

### 1.2 子弹穿障 —— 根因：设计意图未落地

现状（代码证据）：
- `Bullet.update`（HTLM/js/combat.js:1078）全函数 **0 处障碍检测**——子弹飞行全程无视障碍。
- 「障碍物挡弹道」只做在**索敌阶段**：`losClear`（slab 法线段 vs AABB）保证「不打障碍后的怪」，combat.js:576 注释「锁住障碍后的怪只会让子弹打在障碍上」。
- 但子弹本身不撞障碍 → 玩家隔墙输出、敌人隔墙压制，与 losClear 的设计意图自相矛盾。

### 1.3 附带发现（同一病灶）

- 投放点采样（findFreeSpot）、祭坛/信标净空都靠 `blockedByObstacle` 逐点全量遍历，同一 O(N×M) 问题。

## 二、修复方案：Godot 重建（主战场）

原则：**HTML 版是设计真源，但不是工程真源**。寻路这类架构级缺陷，在 Godot 里按正确架构重建，而不是把 bug 逐行翻译过去。

### 2.1 分层寻路（业界标准答案）

| 层 | 方案 | 适用 | 成本 |
|---|---|---|---|
| **全局层** | **Flow Field（流向场）** | 杂兵群（千级） | 全场一次 BFS（~1ms），每怪每帧 O(1) 查表 |
| **个体层** | Steering（分离力 + 墙避让） | 怪间挤开、贴墙滑行 | O(邻域)，SpatialHash 查邻居 |
| **精确层** | Godot NavigationServer2D（NavigationAgent2D） | 精英怪 / Boss（个位数） | 引擎原生，每代理有开销，仅少量单位用 |

**Flow Field 原理**（弹幕肉鸽群体的正解，Vampire Survivors、They Are Billions、Supreme Commander 2 同路数）：
1. 每帧（或每 0.2s 节流）从玩家位置 BFS 全图可行走格，得到「每格 → 玩家的最短方向」一张流场图；
2. 所有怪查自己所在格的方向向量 + 与邻格方向插值 → 直接得到前进方向；
3. 玩家移动只触发流场增量更新，千怪共享一张图，**怪越多边际成本越低**——这正是「群体追一个目标」场景 flow field 胜过逐怪 A* 的原因。

**Godot 落点**：`mods/jes-engine-core/scripts/flow_field.gd`（新增，P1 空间层扩展）+ 障碍注册进 SpatialHash（一并解决 O(N×M)）。

### 2.2 子弹 vs 障碍（对齐设计意图）

方案：**步进检测 + SpatialHash 查询**
- 子弹每帧位移拆成 substep（每步 ≤ 子弹半径），逐步查 SpatialHash 里的障碍格 → 防高速隧穿；
- 命中障碍 → 子弹 vanish（对齐《全新技能系统设计书》事件口径：正常消失，按规则派生），不补 hit；
- 敌方子弹同样处理（隔墙压制消失）。
- 性能：障碍数量少（每世界十几~几十个），SpatialHash 查询 O(1) 均摊，3000 弹主线无压力。

### 2.3 验收标准（先定义「坏掉长什么样」再动手）

| 指标 | 定义 | 目标 |
|---|---|---|
| 卡死率 | 怪连续 3 秒位移 < 20px 且目标在 200px 外，计卡死 | < 0.1%（压测 1500 怪场景） |
| 穿障率 | 子弹路径与障碍 AABB 相交却存活过墙 | 0（回归测试断言） |
| 寻路帧耗 | flow field 更新 + 全怪查表 | < 1.5ms p95 |

## 三、修复方案：HTML 热修（可选，仅当需在网页版先验证手感）

若想在网页版先验手感，最小热修两刀（改 js/game.js + js/combat.js 末尾独立区块，铁律 2）：

1. **卡死逃逸**：怪记忆 `_stuckT`（连续未接近目标时长），超 1.5s → 临时把目标切到「沿墙方向的远点」绕行，绕出后恢复。不引入全局寻路（HTML 版改不动架构）。
2. **子弹撞墙**：`Bullet.update` 里复用 `losClear`（已是 slab 法）做「上一帧位置 → 本帧位置」线段检测，命中即 dead。子弹量按 CFG.bulletBudget 预算内，每帧 ~几百次线段检测可承受。

> 我的立场：**热修只做手感验证，不做长期维护**。寻路正确的家在 Godot 的 flow field，HTML 版花大架构改造属于把旧房子精装修。

## 四、参考案例

- **Vampire Survivors**：群体怪 = 直追 + 分离力，无逐怪寻路——证明「群体杂兵」不需要 A*；
- **They Are Billions / Supreme Commander 2**：flow field 处理海量单位共享目标寻路的经典；
- **Godot 官方**：NavigationServer2D 文档明确建议「大量单位共享路径时用 flow field 而非每代理寻路」；GitHub 有多个 Godot flow field 开源实现可参考实现细节（选星标高的对照思路即可，不直接搬代码）。

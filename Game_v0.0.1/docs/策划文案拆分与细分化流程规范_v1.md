# 游戏策划文案拆分与细分化 · 通用流程规范 v1.0

> 版本 v1.0　｜　2026-10-26　｜　出处：`docs/XXX游戏名-总流程/策划文档/001-主菜单/` 实战验证
> 用途：**任何游戏**都能直接套用这套拆法，把一个大策划书拆成能分工、能验收、能改的小文档。
> 试用样本：001-主菜单（13 份文件，已通过用户验收，格式定型）

---

## 〇、一页看懂

| 步骤 | 干什么 | 产出 |
|---|---|---|
| 1 | **数按钮**：这一屏有几个能点的东西 | 入口清单 |
| 2 | **建目录**：编号-界面 → A001/A002 → B00X-功能 | 目录树 |
| 3 | **写总纲**：整屏全貌、坐标、配色、能/不能 | `A001-...总文案.md` |
| 4 | **写单功能**：一个功能一份，不合并 | `B00X-{功能}.md` × N |
| 5 | **画图**：整屏一张 + 每个功能一张，真 `.svg` | `*.svg` × N+1 |
| 6 | **做预览**：一页滚完所有图 | `_预览-全部SVG.html` |
| 7 | **自查**：9 项清单全绿 | 检查通过 |
| 8 | **收问题**：把各文档末尾的选择题收拢 | 一次问完 |
| 9 | **验收**：先只做一屏，确认格式后再推下一屏 | 用户点头 |

> **第一条铁律**：先做**一屏**给用户看，他说「格式对了」再推第二屏。绝不一口气写完所有屏——格式错了就是全盘重做。

## 一、为什么必须拆（三个理由）

| 理由 | 不拆的后果 | 拆了的好处 |
|---|---|---|
| 改动成本 | 一份 3 万字文档，改一个按钮要通读全文 | 只动 `B003-设置/`，别的不碰 |
| 分工成本 | 没法把「设置」单独外包 | 整份可以给出去，接口清楚 |
| 查找成本 | 想知道音量怎么写，全文搜 | 路径本身就是答案 |

**拆到什么粒度**：**一个能点的东西 = 一份文档**。按钮、卡片、NPC、滑杆都算。纯展示的（标题、背景、版本号）不拆，写进总纲。

## 二、通用目录结构（复制就用）

```
docs/{项目名}-总流程/
├── 策划文档/
│   └── {001~00N}-{界面名}/
│       ├── A001-策划文案-{界面名}/                    ← 文案类（规则、数值、边界）
│       │   ├── B001-{功能名}/B001-{功能名}.md
│       │   ├── B002-{功能名}/B002-{功能名}.md
│       │   └── ...
│       ├── A001-策划文案-{界面名}总文案.md             ← 这一屏的总纲
│       ├── A002-UI层-SVG文档-{界面名}/                ← 图示类（画在哪、多大、什么色）
│       │   ├── B001-{功能名}/B001-{功能名}.svg        ← 真矢量图
│       │   ├── B002-{功能名}/B002-{功能名}.svg
│       │   └── ...
│       ├── A002-UI层-{界面名}总SVG文档.svg             ← 整屏总图
│       ├── A002-UI层-{界面名}总SVG文档.md              ← 总图的文字说明
│       └── _预览-全部SVG.html                        ← 本屏所有图排一页
├── 程序文档/                                         ← 留位：实现细节、接口约定
└── 美术文档/                                         ← 留位：资源清单（尺寸/命名/数量）
```

### 编号规则

| 编号 | 含义 | 谁定 |
|---|---|---|
| `001~00N` | 按**玩家实际走的顺序**编，不按重要性 | 固定 |
| `A001` | 文案类（规则、流程、数值、边界、存档） | 固定 |
| `A002` | 图示类（坐标、尺寸、颜色、四态） | 固定 |
| `B001~B00X` | 这一屏的具体功能，**每屏从头编** | 每屏独立 |

**为什么 A001/A002 两类**：同一个功能，策划关心「什么规则」，美术关心「长什么样」。混在一份里，两边都觉得啰嗦，且改样式会误伤规则。

**B 编号怎么排**：按**功能重要性**排，主路径永远 B001（例：主菜单视觉顺序是「开始、操作、设置、图鉴、退出」，但 B001 是开始游戏，B005 才是操作说明）。

## 三、动手前的第一件事：数按钮

| 步骤 | 做法 |
|---|---|
| ① 对着代码/原型截图，抄下所有能点的东西 | 按钮、卡片、NPC、滑杆、可拖拽格子全算 |
| ② 一个能点的 = 一个 B00X | 不许合并，合并就会「改一个动全部」 |
| ③ 纯展示的不建 B00X | 标题、副标题、背景、版本号 → 只进总纲元素清单 |
| ④ 补漏 | 实际界面有、但原始骨架里没有的，必须补编号（例：主菜单真有个「操作说明」按钮，骨架漏了 → 补 B005） |

> 这一步做错，后面所有文档全白写。**数两遍再动手。**

## 四、总纲模板（每屏一份，最长的一份）

文件名：`A001-策划文案-{界面名}总文案.md`

| 章节 | 必填 | 内容 | 给谁看 |
|---|---|---|---|
| 头部引用块 | ✅ | 版本、日期、**对应代码文件+行号**、上游界面、下游界面 | 开发 |
| 一、这一屏是干什么的 | ✅ | 一句话说清 + 2~3 条设计底线 | 决策者 |
| 二、界面元素清单 | ✅ | 逐个元素：内容 / 可点否 / 归哪份 B 文档 | 双方 |
| 三、界面布局 | ✅ | **文字 ASCII 图**，元素旁标 y 坐标与字号 | 决策者 |
| 四、颜色规格 | ✅ | 全局色板表，注明「以后每屏只从这里挑」 | 美术 |
| 五、能做和不能做的事 | ✅ | ✅ 表格 + ❌ 表格（❌ 才是重点） | 双方 |
| 六、和其他文档的约定 | ✅ | 数据从哪来、告诉谁、缺什么数据源 | 开发 |
| 七、实现状况 | ✅ | **真话**，✅🟡❌ 三色，不许美化 | 决策者 |
| 八、待办清单 | ✅ | 编号 T1…Tn、为什么重要、谁定 | 双方 |
| 九、文件索引 | ✅ | 所有 B00X 一览 | 双方 |
| 十、待拍板事项 | ✅ | **只放真要决策者选的**，不拿技术题烦他 | 决策者 |

### 三条硬要求

1. **代码行号不许编**。写 `flow_root.gd _build_main()` 第 302~341 行，就必须真去数。行号是唯一能证明「文档对得上代码」的东西。
2. **实现状况必须诚实**。半成品写 🟡 并说明差在哪。整个机制的用途就是防止「文档很美好、产品很破烂」。
3. **ASCII 布局图用全角框线**，右侧标 y 坐标。非技术读者靠它理解上下顺序。

## 五、单功能模板（一个按钮一份）

文件名：`A001-策划文案-{界面}/B00X-{功能}/B00X-{功能}.md`

| 章节 | 必填 | 内容 |
|---|---|---|
| 头部引用块 | ✅ | 父级界面、版本、日期、**对应代码行号** |
| 一、这个功能是干什么的 | ✅ | 一句话 + 对目标玩家的意义 |
| 二、界面长什么样 | ✅ | 尺寸/字号/颜色/圆角/位置的精确表格 |
| 三、点击后发生什么 | ✅ | 完整流程 ①②③④⑤，**带耗时** |
| 四、各种状态 | ✅ | 常态 / 悬停 / 按下 / 禁用，四态齐全 |
| 五、声音/反馈 | 按需 | 有音效才写，写清时机和音量 |
| 六、异常情况 | ✅ | 出错怎么处理 + 用户看到什么 |
| 七、不许干的事 | ✅ | ❌ 表格，防后期跑偏 |
| 八、和其他文档的约定 | ✅ | 输入 / 输出 / 依赖 / 前置 |
| 九、实现状况 | ✅ | ✅🟡❌ + 一句「要补的」 |
| 十、待拍板事项 | 按需 | **2~3 个**多选项，多了招人烦 |

### 可选章节（复杂功能才加）

| 章节 | 触发条件 | 例子 |
|---|---|---|
| 数值表 | 有具体数字要配 | 怪物血量、经验曲线、掉落权重 |
| 存档规则 | 会产生持久数据 | 设置项、解锁记录、货币 |
| 分区明细 | 一块里分几类 | 图鉴分英雄区+怪物区 |
| 优先级分层 | 功能有 P0/P1/P2 | 主城 8 个 NPC |
| 玩法循环图 | 有「重复做什么」的结构 | 战斗→撤离→养成 |

## 六、图示规格（这一步最容易出错）

### 6.1 一个功能一张图

| 图 | 内容 |
|---|---|
| 整屏总图 | 这一屏整体长什么样，1:1 实尺寸，虚线标关键尺寸 |
| B00X 单图 | 这个组件的所有状态并排（常态/悬停/按下/禁用） |

### 6.2 每张图必须画出来的 5 样

| 必画 | 说明 |
|---|---|
| 外形 | 与目标分辨率 1:1 的画布，能量像素 |
| 标注 | 虚线 + 数字，标关键宽高与起点坐标 |
| 各状态并排 | 摆一起对比，不许分散在多张图 |
| 颜色值 | 直接写 `#e8b33c`，美术能抄 |
| 行为小字 | 「拖动即刻生效」这类规则用灰字写图角（产品内不显示） |

### 6.3 SVG 技术硬要求（跨游戏通用）

| 要求 | 值 |
|---|---|
| 根元素 | `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 W H" width="W" height="H">` |
| 字体 | 写 2~3 个中文字体兜底：`'Noto Sans SC','Microsoft YaHei','PingFang SC',sans-serif` |
| 中文 | 直接写中文，不要转义成实体 |
| 渐变/阴影 | 全部放 `<defs>`，id 加前缀防冲突（`mnBg`/`mnShadow`） |
| 禁止 | 不引用外部图片、不引用外部字体文件——必须能离线双击打开 |
| 文字基线 | `y` 是基线不是顶边，行高约 1.35 倍字号；中文标题居中用 `text-anchor="middle"` |

### 6.4 预览页（重要，非技术用户唯一入口）

在界面根目录生成 `_预览-全部SVG.html`：把所有图按「总图 → B001 → B002…」竖排，深色底，宽 100%。

> 决策者双击一个文件、往下滚一遍就看完全部图。这是整套流程里**最影响验收效率**的一个小文件。

## 七、交付前自查清单（9 项，每次必过）

| # | 检查项 | 怎么查 |
|---|---|---|
| 1 | 所有 SVG 的 XML 合法 | `xml.dom.minidom.parse()` 逐个过 |
| 2 | 所有 SVG 画布尺寸 = 目标分辨率 | 读根元素 width/height |
| 3 | 没有 `XXX-SVG.md` 这种混名 | 文件名全文搜索 |
| 4 | 文件名 = 所在文件夹名 | 逐个比对 |
| 5 | 每个 B00X 都有 `.md` 和 `.svg` 各一份 | 数量比对 |
| 6 | 每份文档都有「实现状况」章节 | 全文搜索 |
| 7 | 每份文档的代码行号真实存在 | 打开源文件核对 |
| 8 | 预览页能打开、图都在 | 浏览器打开看 |
| 9 | 总索引文件已更新（界面状态、文件数） | 核对数量 |

**一句话**：图是给非技术决策者看的，行号是给开发看的，两张都必须是真的。

## 八、文件命名硬规则（踩过的坑，写死）

| 规矩 | 反面例子 |
|---|---|
| `.svg` 里**只放图**，不放说明文字 | — |
| 说明文字一律 `.md` | — |
| **禁止 `XXX-SVG.md`**：既不是图，也不是纯说明 | ❌ `B004-退出游戏-SVG.md` |
| 文件名 = 文件夹名 | ❌ `B001/开始游戏图.svg` |
| 编号与名称用 `-` 连，中间不断空格 | ❌ `B005 操作说明.md` |
| 整屏总图放界面根目录，不放 A002 子目录 | ❌ `A002.../总图.svg` |
| 总图命名 `A002-UI层-{界面名}总SVG文档.svg` | ❌ `001-主菜单-参考图.svg` |

> 这些不是洁癖。名字乱了以后，非技术决策者找不到文件，等于没做。

## 九、和「非技术决策者」协作的规矩

| 规矩 | 说明 |
|---|---|
| 只给按钮，不给问答题 | 多选项式提问，让他点，不要写一长段等他回 |
| 一次最多 4 题 | 多了他烦，剩下的下一轮 |
| 不拿技术题烦他 | 「用 CanvasLayer 还是 Control」自己定，只报结论 |
| 选择题集中在文档最后一节 | 不许在正文中间打断阅读 |
| 说人话 | 不写「收益阈值」「锚点插值」，写「打到多少给多少」 |
| 报错说后果 | 不写「渲染顺序错误」，写「按钮被后面的东西压住了，看不见」 |
| 每轮交付都要有能点开的东西 | 至少一个可双击的 html/svg，不能只给文字 |
| 先做一屏再推广 | 格式是他验收的，不是自己判断的 |

### 「已定答案」清单（防止重复问）

每做完一屏，把已定的设计决策汇总到总索引里（例：一局多长、失败感受、打完 Boss 算赢、死了丢什么……）。**下次不许再问同样的题**——重复提问是最伤信任的错误。

## 十、每一屏的执行队列（可直接照跑）

```
① 读代码：找到这一屏的构建函数，数清每个可点元素的真实行号
② 列清单：元素写成表（内容 / 可点否 / 归属哪个 B00X）
③ 建目录：mkdir -p 完整目录树
④ 写总纲 A001（一份，最长）
⑤ 写 B00X 文案（N 份，互相独立 → 可并行）
⑥ 画 SVG（N+1 张，先总图后分图）
⑦ 生成 _预览-全部SVG.html
⑧ 跑自查清单 9 项
⑨ 更新总索引（界面状态 / 文件数 / 修正记录）
⑩ 汇报：给预览页 + 收拢所有待拍板选择题
```

**能并行**：④⑤⑥ 文件名定下后就能各写各的（文件所有权互不重叠）。
**不能并行**：②必须在①之后（要真行号）；⑧必须在全部写完之后。

## 十一、这套流程的由来（每条规矩都有血）

| 踩过的事 | 得出的规矩 |
|---|---|
| 一屏写一份 3 万字大文档 | → 一个功能一份，改一处不牵动全局 |
| 把 UI 规格塞进策划文案里，美术看得累、策划改样式时误伤规则 | → A001 文案 / A002 图，两类分家 |
| A002 里写了 `B004-退出游戏-SVG.md`（内容是文字不是图） | → `.svg` 只放图，禁 `-SVG.md` |
| 6 张图要一张张点开，决策者嫌烦不看 | → 必生成 `_预览-全部SVG.html` |
| 文档写「✅ 已完成」，实际是空壳 | → 强制「实现状况 ✅🟡❌」章节，写假话一眼看得出 |
| 文档写「对应 xxx.gd 第 300 行」，实际不在此处 | → 行号必须真数，它是文档与代码的唯一桥 |
| 一次问 10 个问题，决策者直接不回 | → 一次最多 4 题，只问真需要他选的 |
| 一口气写完 7 屏，格式不合口味全部重做 | → **先做一屏，验收后再推** |

## 十二、套用到新游戏的启动清单

换一个游戏，只需替换这三样，其余照抄：

| 要替换 | 怎么定 |
|---|---|
| ① 界面清单 | 按「玩家打开游戏→…→关掉游戏」的顺序数一遍，每个界面一个编号 |
| ② 目标分辨率 | 决定 SVG 画布尺寸（例：1280×720 / 1920×1080 / 750×1334 竖屏） |
| ③ 全局色板 | 定 6~8 个颜色，全部编号命名，之后每屏只从里面挑 |

然后把本文的模板复制成第一屏的文档，做完给决策者验收。

### 启动检查项

- [ ] 界面清单定完，编号连续无跳号
- [ ] 目标分辨率定完，写进本文第 6.3 节
- [ ] 全局色板定完（≤8 色），写进每屏总纲第四节
- [ ] 第一屏的「数按钮」清单经二次核对
- [ ] 第一屏只用一屏试格式，不连带做第二屏

## 附：文件数量速算

一屏文件数 = 1（总纲 md） + 1（总图 svg） + 1（总图说明 md） + 1（预览 html） + N×(1 md + 1 svg)

> 例：主菜单 N=5 → 4 + 10 = **14 份**（含 `_预览`）。
> 估算工作量时按这个公式算，别凭感觉。

- 书稿版本：v0.1
- 设计口径正本：v0.5
- 状态：第一版完整书稿，供其他 AI 和项目成员理解、评审与继续设计。
- 正本关系：本书解释和组织正本，不替代正本；本书中的“推荐草案”没有经过金弋顺选择前，不得冒充已确认规则。
- 代码状态：不包含实现代码。
- 参数状态：不开启最终参数表；案例中的数量和时间仅用于说明。

## 设计原则

1. **先区分单位，再讨论数量。**施放、动作、出手、实例、命中和伤害份数不是同一个单位。
2. **先区分时间轴，再讨论流程。**施法者和效果体不是一条连续攻击长链。
3. **事件要少而稳定。**当前效果体事件只有 `hit` 与 `vanish`。
4. **效果体是容器，事件是点。**一个效果体可以没有事件，也可以在生命周期内多次命中。
5. **判定与表现分离。**抛物线、贝塞尔曲线和顺逆时针旋转默认只负责好看。
6. **细节由 AI 先补方案。**未确定处不能只丢问题；应先给出候选、优缺点、推荐理由和案例，再由项目负责人选择或纠正。
7. **外部资料只做事实核验。**参考资料不能替代项目方向，也不能整套搬入本系统。

# 第一部　如何阅读本书

<a id="第1章　本书解决什么问题"></a>
# 第1章　本书解决什么问题

## 1.1 这不是一本“技能名词表”

技能系统最容易出现的问题，不是没有足够多的攻击类型，而是把不同层级的词混在一起：

- 把“攻击动作”当成“出手次数”。
- 把“飞弹”当成“命中”。
- 把“多个伤害数字”当成“多个 `hit`”。
- 把“炮弹落地”写成“施法者攻击结束”。
- 把“持续火区的一次跳伤”写成角色重新施放技能。
- 把抛物线、旋转方向等表现，误当成碰撞判定。
- 把水晶和遗物拆成两套互不相容的技能系统。

本书的目标，是让任何读者都能对同一个技能回答同一组问题：

1. 谁在运行这段流程？施法者，还是效果体？
2. 这次攻击何时真正出手？
3. 出手产生了多少攻击实例？
4. 实例如何运动、等待、追踪或滞留？
5. 何时发生 `hit`？一次接触产生几条 `hit`？
6. 一条 `hit` 内有多少伤害份？每份如何判闪避？
7. 实例何时终止？是否发送 `vanish`？
8. 是否由 `hit` 或 `vanish` 派生新的实例？
9. 水晶或遗物修改的是已有数字、行为，还是场上实例？
10. 玩家看到的技能文字，应该写哪部分？

## 1.2 本书的适用边界

本书覆盖：

- 施法者闭环与效果体生命周期。
- `hit`、`vanish`、派生和终止。
- 无载体、自身载体、独立载体。
- 连发、齐发、重复命中与一次命中内多份伤害。
- 逐份闪避与伤害减免的基本顺序。
- 波前、开始延迟、持续区域和火区。
- 水晶、遗物和三档修饰权限。
- 面向玩家和面向 AI 的技能文档写法。
- 代表性技能案例与评审清单。

本书不包含：

- 旧代码的类名、函数名或行号。
- 最终参数数值表。
- 最终伤害公式、护甲曲线或全部状态词缀体系。
- 旧的四水晶槽、五档稀有度、背包容量和全局子弹预算方案。
- 未经项目负责人确认的工程实现细节。

## 1.3 一条最重要的阅读原则

**本书中出现的规则，必须先看它的状态。**

- 写着“已确认”的，是当前项目口径。
- 写着“推荐草案”的，是冰冰提出的候选，不等于金弋顺已经批准。
- 写着“案例”的，是为了验证概念，不等于正式数值。
- 写着“外部事实”的，是资料能支持的引擎或参考信息，不等于本项目必须采用。

# 第2章　状态标签与权威层级

## 2.1 权威层级

当不同材料出现冲突时，按以下顺序处理：

1. 金弋顺最新明确确认的口头或书面口径。
2. 《技能系统口径手册》的最新版本。
3. 本书中已经从正本准确整理出的“已确认”内容。
4. 本书中的“推荐草案”和案例。
5. 外部资料、参考游戏和搜索文章。
6. AI 自己的默认习惯。

最低层级的内容不能推翻上层内容。特别是，不能因为其他游戏或引擎常这样做，就说本项目已经这样决定。

## 2.2 四种状态

| 状态 | 含义 | AI 应如何处理 |
|---|---|---|
| 已确认 | 项目负责人明确确定的规则 | 直接遵守，不重复提问 |
| 可直接推出 | 由已确认规则和常识必然得到的结果 | 直接整理，不把常识包装成选择题 |
| 推荐草案 | AI 为未定细节提出的完整方案 | 说明优缺点和推荐理由，等待项目负责人审改 |
| 未决定 | 仍存在真正的玩法分歧 | 先给 2—3 个可执行候选，不把空白直接丢回用户 |

## 2.3 当前正本的核心状态

当前设计口径正本为 v0.5，核心状态如下：

- 两条时间轴已锁定。
- 事件只有 `hit` 与 `vanish`。
- 三类载体已锁定。
- 多份伤害分别判断闪避已锁定。
- 全部伤害份被闪避时不产生 `hit` 已锁定。
- 连发、齐发、连中和命中内多份伤害必须分开描述已锁定。
- X 的整轮出手含义可继续作为讨论用语。
- Y、Z 的新字母分配仍未最终锁定。
- 动作与出手的组织、前摇覆盖范围、冷却起点和多次出手节奏仍可用候选方案推进。
- 本书不会因为“方便 AI 阅读”而偷偷把候选写成已定规则。

<a id="第3章　给后续-ai-的阅读与协作协议"></a>
# 第3章　给后续 AI 的阅读与协作协议

## 3.1 AI 先做什么

后续 AI 读取本书或正本后，必须先恢复以下骨架：

```text
施法者：索敌决定 → 可选前摇 → 瞬时出手 → 冷却 → 回到索敌
效果体：生成 → 存活／运动 → 0 到 N 次 hit → 终止 → 按规则派生 → 回收
事件：只有 hit、vanish
载体：无载体、自身载体、独立载体
```

然后再分析具体技能。不能先从“这是近战还是远程”开始套模板。

## 3.2 AI 不得重复询问的内容

下列内容已经明确，不应再次让用户确认：

- 每份伤害分别判断闪避。
- 闪避成功则跳过该份。
- 未闪避才计算该份伤害和减免。
- 所有份都闪避则不产生 `hit`。
- 至少一份未闪避时，本次对该目标成立一条 `hit`。
- 多份伤害不自动增加 `hit` 条数。
- 持续区域每一跳若命中，仍然是 `hit`，不是新事件。
- 施法者和效果体不是同一条链。

## 3.3 AI 遇到真正未定项怎么办

不能只问：“你想怎么做？”

应该交付：

1. 问题是什么。
2. 为什么会影响玩法或实现。
3. 方案 A、B、必要时 C。
4. 每个方案的优点。
5. 每个方案的代价和风险。
6. 推荐哪个，以及为什么。
7. 一个具体技能案例。
8. 项目负责人只需选择、修改或否定，不需要从零发明架构。

## 3.4 AI 输出新技能时的最低结构

任何新技能至少要先写：

- 技能意图。
- 施法者层一流程。
- 每个效果体的载体与层二生命周期。
- 命中和终止条件。
- 伤害份与闪避处理。
- 派生模型。
- 玩家文字。
- 当前确认项与推荐草案。

如果技能含穿透、分裂、弹射、连锁或持续区域，还必须明确其具体模型。

# 第二部　技能系统的底层模型

<a id="第4章　两条时间轴"></a>
# 第4章　两条时间轴

## 4.1 施法者闭环

施法者侧的基本流程是：

```text
索敌决定 → 起手／前摇（可选）→ 出手 → 冷却 → 回到索敌
```

### 索敌决定

索敌决定不是“让所有飞弹持续找目标”。它负责决定本轮是否具备出手条件，以及本次出手使用什么目标、方向或地面位置。

### 前摇

前摇是出手前的准备阶段。前摇时长可以为零；若前摇尚未完成，对应出手不能发生，也不能提前生成效果体。

蓄力完成不是事件。它只是前摇结束并允许出手的条件。

### 出手

出手是瞬时交接点。它可以：

- 直接做一次瞬时范围判定。
- 改变施法者坐标。
- 让施法者进入自身载体运动。
- 生成一个独立效果体。
- 同时完成位移和生成效果体。
- 生成多个攻击实例。

出手不是“播放完整攻击动作”的同义词，也不是“一颗飞弹”的同义词。

### 冷却

冷却属于施法者层一，是对后续出手或后续施放的限制。冷却不是效果体的寿命。

对于多次连续出手，前摇覆盖整轮还是单个动作、冷却从哪一个时间点开始，暂以推荐方案推进，但没有自动成为最终口径。

## 4.2 效果体生命周期

每个效果体实例独立走：

```text
生成 → 存活／运动 → 命中 0 到 N 次 → 终止 → 按规则派生 → 回收
```

这不是一条“每一步只发生一次”的线：

- 命中可能发生零次。
- 命中可能发生多次。
- `hit` 可以发生在实例终止前。
- `hit` 可以派生子实例，而父实例继续存活。
- 终止不一定发送 `vanish`。
- `vanish` 也不保证一定派生。
- 回收不是事件。

## 4.3 两条时间轴如何交接

一次出手生成独立效果体后，效果体从生成开始进入层二。它不再重新走施法者的前摇和冷却。

例如：

```text
施法者：索敌 → 前摇 → 出手 → 冷却 → 再次索敌
                         │
                         └── 炮弹：生成 → 飞行 → hit 0~N → 终止 → vanish/派生 → 回收
```

施法者可以已经进入冷却，而炮弹仍在飞；火区可以已经存在，而施法者已经准备下一轮出手。它们是并行关系，不是“攻击还没结束所以施法者不能离开攻击状态”。

## 4.4 错误的单链写法

下面这句不能作为正式流程：

```text
索敌 → 蓄力 → 施法时 → 攻击进行中 → 飞行与命中 → 攻击结束 → 冷却
```

问题在于：

- “飞行”不是施法者状态。
- “命中”不是施法者状态。
- “攻击结束”可能指角色动画结束，也可能指炮弹终止，含义不明确。
- “火区持续伤害”会被错误地塞到施法者的攻击中。

科学的表达应拆成施法者闭环和效果体生命周期。

# 第5章　效果体生命周期

## 5.1 效果体是容器

效果体是承载一段战斗行为的容器，不是某一个事件。

一个炮弹效果体可以：

- 生成后飞行。
- 飞行中命中一次。
- 命中后继续穿透。
- 再命中两次。
- 飞行距离耗尽后发送 `vanish`。
- 由 `vanish` 派生火区。
- 回收自身。

也可以完全没有命中，只在到达终点后正常结束。

## 5.2 生成

生成是实例开始存在，不是事件。

一次出手可以生成 0 到 N 个实例。生成数量不能直接等同于出手次数，也不能直接等同于命中次数。

## 5.3 存活与运动

存活与运动包括：

- 飞行。
- 等待开始。
- 静止滞留。
- 环绕。
- 回旋。
- 追踪。
- 波前扩张。
- 半径变化。
- 沿路径移动。
- 等待某个时间后进入可命中状态。

“运动”不代表一定向前飞；一个静止火区也属于独立载体的存活过程。

## 5.4 命中

命中是瞬时的 `hit`。它发生在效果体生命周期内部。

命中后可能：

- 结束当前实例。
- 继续运动。
- 修改当前实例目标。
- 由 `hit` 派生新的实例。
- 对同一目标以后再次命中。

这些行为都需要技能本身声明，不能仅凭“命中”二字自动推导。

## 5.5 终止、派生、回收

终止表示当前实例结束。终止本身不是事件。

如果这次正常终止发送 `vanish`，可以按技能规则由 `vanish` 派生新实例。先完成需要读取父实例信息的派生，再回收父实例。

如果是强制清场、阵亡清理或场景卸载，推荐走“不发送 `vanish` 的管理回收”路径，不因为清理而留下额外爆炸、火区或子弹。

---

<a id="第6章　事件条件结算标记与状态"></a>
# 第6章　事件、条件、结算标记与状态

## 6.1 事件只有两个

| 事件 | 含义 | 典型来源 |
|---|---|---|
| `hit` | 一次命中成立 | 飞弹接触目标、区域一次跳伤、波前第一次覆盖目标 |
| `vanish` | 一个实例发送消失事件 | 正常终止、正常到期、正常落地结束 |

生成、运动、等待、蓄力完成、动作播完、暴击、格挡和状态到期都不是第三种事件。

## 6.2 事件与结果的关系

伤害是 `hit` 的结算结果，不是第三种事件。

一次已经成立的 `hit` 可以因为减免而造成 0 点伤害，它仍是 `hit`。但所有伤害份都被闪避时，本次并没有成立的 `hit`。

## 6.3 条件不是事件

“目标身上有冰冻”是条件；“本次攻击暴击”是结算标记；“目标被施加燃烧”是状态结果。这些可以参与 `hit` 规则，但不需要新事件名。

例如：

```text
命中 → 读取目标命中前状态 → 若目标已有冰冻，则由 hit 派生冰刺
```

不是：

```text
命中 → 冰冻事件 → 暴击事件 → 派生
```

## 6.4 状态何时成为效果体

状态默认不是效果体。若状态需要拥有独立生命周期，例如：

- 持续存在一段时间。
- 期间周期触发伤害。
- 到期时可以派生爆炸。
- 需要被清场、刷新、叠加或单独修改。

则可以把它建模成效果体。这样它仍然使用既有的 `hit` 与 `vanish`，不增加“状态到期事件”。

---

<a id="第7章　派生终止与回收"></a>
# 第7章　派生、终止与回收

## 7.1 派生的两个入口

派生只能由两个已有事件驱动：

1. `hit` 派生：命中时创建新实例，父实例可以继续存在。
2. `vanish` 派生：实例正常消失时创建新实例。

计时器到点、波前移动到某处、开始延迟结束，都不是新的派生事件。它们可以改变效果体状态，或者让实例进入终止并发送 `vanish`，但不能绕过事件模型。

## 7.2 终止原因必须写清

同一个“消失”画面，可能有不同终止原因：

- 正常命中后消失。
- 飞行距离耗尽。
- 正常落地。
- 持续时间到期。
- 回旋完成。
- 被打断。
- 施法者阵亡后的强制清场。
- 场景卸载。

只有技能允许的正常终止原因，才可以触发对应的 `vanish` 派生。

## 7.3 清场不能制造攻击

如果炮弹因为强制清场被收走：

- 不补发 `hit`。
- 不发送 `vanish`。
- 不生成火区。
- 不生成结束爆炸。
- 直接按管理规则回收。

这是为了避免“角色死亡反而留下额外攻击”的隐式漏洞。

## 7.4 不要把派生写成线性尾巴

正确：

```text
父弹生成 → 飞行 → 命中甲
                    └── hit 派生小弹
父弹继续飞行 → 命中乙 → 终止 → vanish → 回收
```

错误：

```text
父弹生成 → 飞行 → 所有命中结束 → 父弹消失 → 才允许分裂
```

命中派生不需要等待父实例终止。

<a id="第8章　三类载体"></a>
# 第8章　三类载体

## 8.1 无载体

出手时直接完成一次瞬时结算，不产生可运动、可存活的实例。

适用：

- 瞬时扇形。
- 瞬时圆形爆炸。
- 瞬时直线判定。
- 瞬时射线。
- 瞬移本身。

无载体没有自己的存活期，也没有自己的 `vanish`。如果瞬移后要爆炸，应在同一次出手里生成独立爆炸载体，而不是说“瞬移结束后派生”。

## 8.2 自身载体

施法者本人进入效果体侧的运动过程。

适用：

- 冲刺。
- 跳跃。
- 具有路径命中的位移。

路径上的目标是否受伤，由自身载体的判定规则决定。自身载体是否可被打断、被打断是否发送 `vanish`，需要技能或系统规则说明。

## 8.3 独立载体

出手生成后，实例独立运行。

适用：

- 飞弹。
- 炮弹。
- 地震波。
- 地刺。
- 持续火区。
- 回旋投掷。
- 环绕飞刃。
- 持续射线。

独立载体不等于必须飞行。环绕和静止火区都属于独立载体。

## 8.4 近战和远程不是载体表

“近战／远程”是玩家感知和设计分类，不应成为两套底层生命周期。

- 近战可以是无载体瞬时扇形。
- 近战可以是自身载体冲刺。
- 近战可以是独立载体剑气。
- 远程可以是无载体瞬时射线。
- 远程可以是独立载体飞弹。
- 远程也可以是独立载体地面区域。

决定载体的不是距离，而是“这段效果由谁承载、是否需要独立存活过程”。

# 第三部　攻击、命中与伤害

<a id="第9章　判定维度与表现维度"></a>
# 第9章　判定维度与表现维度

## 9.1 五个沟通维度

为了描述技能，建议按五个维度拆开：

1. **载体：**无载体、自身载体、独立载体。
2. **判定形状：**圆、扇形、直线、射线、判定半径、角度和长度。
3. **运动方式：**飞行、追踪、环绕、回旋、波前、等待、滞留。
4. **命中与派生行为：**穿透、分裂、弹射、连锁、命中后消失、结束后留场。
5. **视觉表现：**抛物线、贝塞尔曲线、拖尾、顺时针或逆时针旋转。

这是设计沟通结构，不代表最终代码类结构。

## 9.2 默认只负责表现的参数

以下内容默认不参与命中：

- 抛物线。
- 贝塞尔曲线。
- 顺时针或逆时针旋转贴图。
- 只用于显示的扇形边界。
- 拖尾路径。

如果设计希望“扫到才受伤”，就必须明确把扫动写成判定波前。不能一边说旋转只是贴图，一边又根据旋转方向决定目标受伤顺序。

## 9.3 判定参数

以下通常可以参与命中或时机：

- 角度。
- 判定半径。
- 射线宽度。
- 直线长度。
- 载体移动速度。
- 波前速度。
- 生成数量。
- 开始延迟。
- 生成间隔。
- 滞留时长。
- 追踪、环绕、回旋的运动判定。

一个参数只能在技能明确声明时跨越“表现”和“判定”的边界。

<a id="第10章　连发齐发连中与多份伤害"></a>
# 第10章　连发、齐发、连中与多份伤害

## 10.1 连发

连发是先后发生了多少次瞬时出手。

例如：

```text
出手① → 出手② → 出手③ → 出手④ → 出手⑤ → 出手⑥
```

这里是六次出手。它不自动说明：

- 播放了几次动作。
- 生成了几颗飞弹。
- 命中了几次。
- 每次间隔是多少。
- 每次出手是否重新支付前摇和冷却。

## 10.2 齐发

齐发是同一次出手同时展开多少份攻击。

例如：

```text
一次出手 → 左、中、右三颗独立飞弹
```

仍然只有一次出手，但生成了三个攻击实例。

齐发攻击份数不保证：

- 每一份都会命中。
- 每一份同时抵达。
- 每一份都对同一目标生效。
- 每一份都对应一条 `hit`。

## 10.3 连中／重复命中

重复命中是效果体或多个攻击实例实际产生多条 `hit`。

例子：

- 持续火区每次伤害时机对同一目标产生一条 `hit`。
- 穿透飞弹先命中甲，再命中乙，产生两条 `hit`。
- 两颗齐发飞弹分别命中同一目标，产生两条独立 `hit`，即使发生在同一结算帧。

同一效果体能否重复命中同一目标、两次命中的最小间隔和命中次数上限，必须由技能说明。

## 10.4 一次命中内多份伤害

一次 `hit` 可以包含多份伤害结算：

```text
一次接触 → 一条 hit → 伤害份 A、伤害份 B、伤害份 C
```

这不是三条 `hit`，也不是三个连续命中。

多份伤害可以：

- 是相同类型的多份伤害。
- 是不同类型的伤害。
- 使用不同的减免规则。
- 有不同的闪避结果。

但无论画面显示几个数字，它们仍然属于同一条 `hit`，除非技能明确产生了多次独立命中。

## 10.5 四个概念的关系

```text
连发：一次施放里有多少个先后出手点
  ↓
齐发：每个出手点展开多少份攻击实例
  ↓
实例运行：运动、等待、追踪、滞留
  ↓
重复命中：实际产生多少条 hit
  ↓
命中内多份伤害：每条 hit 内包含多少份伤害结算
```

不能用“连发 × 齐发 × 伤害份数”直接推导最终命中次数或总伤害。中间还受到运动、落空、目标位置、重复命中限制和逐份闪避影响。

<a id="第11章　一次命中的逐份结算"></a>
# 第11章　一次命中的逐份结算

## 11.1 当前已确认的顺序

对一次候选接触中的每份伤害，执行：

```text
判断该份是否闪避
    ├─ 闪避成功：跳过该份
    └─ 未闪避：计算该份伤害与适用减免
```

最后：

- 如果所有份都被闪避：本次未命中，不产生 `hit`。
- 如果至少一份未被闪避：本次命中成立，只产生一条 `hit`。
- 未闪避但被减免到 0：仍然是已经成立的 `hit`，不等于闪避。

## 11.2 部分闪避案例

一次接触包含三份伤害：

| 伤害份 | 闪避结果 | 伤害处理 | 本次命中结果 |
|---|---|---|---|
| A | 被闪避 | 跳过 | 不单独产生 `hit` |
| B | 未闪避 | 计算伤害和减免 | 组成同一条 `hit` |
| C | 未闪避 | 计算伤害和减免 | 组成同一条 `hit` |

结论：本次有一条 `hit`，不是两条。

如果 A、B、C 全部被闪避，则没有 `hit`，也不执行这次 `hit` 驱动的派生。

## 11.3 每份伤害独立计算，不等于每份必须是不同伤害类型

“每份分别计算”表示结算粒度不同，不强制要求每份内容不同。

例如：

- 三份相同火焰伤害：仍然逐份判闪避、逐份算减免。
- 一份物理、一份火焰：分别适用对应减免。
- 一份直接伤害、一份护盾伤害：可以有不同结算路径，但需要技能或伤害规则明确支持。

## 11.4 命中规则不要按伤害份数重复执行

一次 `hit` 内有三份伤害，不代表：

- 命中分裂执行三次。
- 命中后施加状态三次。
- 命中音效播放三次。
- 命中派生子弹三批。

推荐由“一条 `hit`”驱动规则一次执行；一条规则内部可以声明生成多个孩子，但不能因为伤害份数自动复制规则。

## 11.5 结算公式的状态

逐份闪避和逐份处理已经确认，但下列内容仍需要以后用候选方案推进：

- 暴击按份还是按整条 `hit`。
- 格挡按份还是按整条 `hit`。
- 百分比减免的叠加顺序。
- 护甲、护盾、吸血的参与顺序。
- 内部精度与显示取整。
- 伤害数字显示合计还是分份。

AI 不应因为“闪避已逐份”就擅自宣布暴击、格挡等机制也必须逐份。

<a id="第12章　范围波前延迟与持续区域"></a>
# 第12章　范围、波前、延迟与持续区域

## 12.1 范围伤害不一定是瞬时伤害

圆形、扇形和射线只描述形状，不自动决定是否瞬时。

- 瞬时圆形爆炸：无载体，出手时一次判定。
- 扩张圆形：独立载体，半径随时间增加。
- 静止火区：独立载体，在存活期间多次判定。
- 持续射线：独立载体，存活期间沿射线规则多次判定。

## 12.2 波前

波前适合表达“近处先受伤”。

```text
效果体生成 → 判定半径从小到大扩张 → 目标首次被覆盖 → 该目标产生一次 hit
```

波前速度负责受伤顺序，不新增“波前事件”。同一目标是否可在波前返回时再次命中，要另行声明。

## 12.3 开始延迟

一次出手可以生成多个实例，每个实例拥有不同开始延迟。开始延迟不是新的出手，也不是新的事件。

推荐：延迟不占有效作用时长。实例等待结束后，再拥有完整的有效作用期。若设计目标是所有实例同一时刻收束，可以选择“延迟占总寿命”的方案。

## 12.4 持续区域

持续区域是一个独立效果体：

```text
生成区域 → 存活／等待 → 到达伤害时机 → 查找当前范围目标 → 逐份结算 → 等待下一次 → 到期终止
```

区域没有目标时仍然存在。敌人后来进入，可以参加后续伤害时机；敌人离开后，不再自动持续受伤。

一次持续区域的跳伤是多次 `hit`，不是一次 `hit` 内多份未来伤害，也不是角色重新出手。

## 12.5 火区与闪避

火区每个伤害时机对当前范围内的每个目标分别处理：

- 目标 A 全部伤害份被闪避：A 本次没有 `hit`。
- 目标 B 至少一份未闪避：B 本次有一条 `hit`。
- A 的结果不影响 B。
- 某次全部闪避不删除火区。
- 火区不在同一帧无限重试到闪避失败。

<a id="第13章　冷却动作与多次出手"></a>
# 第13章　冷却、动作与多次出手

## 13.1 X 只描述整轮瞬时出手总量

X 仍可用于描述“一轮施放内先后发生了多少次瞬时出手”。

X 不等于：

- 动作播放次数。
- 生成实例数量。
- 命中次数。
- 伤害份数。
- 冷却次数。

X＝0 可表达本轮没有出手，但不自动推出场上已有实例被清除。

## 13.2 双脉冲六次样例

```text
动作一：出手① → 出手②
动作二：出手③ → 出手④
动作三：出手⑤ → 出手⑥
```

当前只用于验证 X、Y 和动作关系，不锁定最终配置组织。

## 13.3 推荐的连发时序草案

当前推荐作为示例的方案是：

```text
整轮起手一次 → 完成计划内多次出手 → 末次出手后进入本轮冷却
```

优点：

- 连发是一组完整动作。
- 增加出手次数不会自动插入多次完整前摇。
- 冷却不会在连发中途结束后立刻插入下一轮。

代价：如果保持出手间隔不变，增加出手会延长整轮占用时间。

这只是推荐草案。某些技能也可以采用“首次出手后开始冷却”或“每个动作组独立起手”，但必须作为技能时序模板明确写出。

## 13.4 动画与逻辑节奏

Godot 官方文档支持通过 Animation 的 Call Method Track 在动画精确时间调用方法，这说明动画标记可以作为一种实现同步路径；但这不能推出项目必须用动画驱动逻辑，也不能把动画回调当成技能系统的新事件。

推荐把“逻辑出手时间”和“动画表现时间”关联但分层：

- 逻辑层决定出手是否发生。
- 动画层表现举杖、炮口火光和后坐力。
- 若动画无法完成，逻辑仍有可验证的时序规则。
- 若需要动画精确卡点，可使用引擎动画轨道作为实现手段。

# 第四部　修饰器与技能组合

<a id="第14章　技能水晶与遗物是同一套修饰器"></a>
# 第14章　技能水晶与遗物是同一套修饰器

## 14.1 两种物品，一套机制

技能水晶和遗物不是两套时间轴，也不是“水晶改层一、遗物改层二”的固定关系。

它们都属于修饰器。差异来自两条限制轴：

1. 允许做什么。
2. 作用到哪些对象。

## 14.2 水晶和遗物的当前默认

当前口径：

| 修饰器 | 改已有数字 | 加行为 | 改场上实例已有数字 |
|---|---:|---:|---:|
| 技能水晶 | 开 | 关 | 未指定 |
| 遗物 | 开 | 开 | 未指定 |

“未指定”不是默认关闭，也不是默认开启。它需要继续用完整候选方案推进。

## 14.3 改数字与加行为

如果技能已经存在飞弹速度、范围半径、波前速度、滞留时长等字段，修改这些字段属于改已有数字。

如果技能原本没有分裂行为，直接写“分裂数量增加”不能凭空创造分裂。让技能获得分裂，是加行为或重配技能。

<a id="第15章　三档权限"></a>
# 第15章　三档权限

## 15.1 `mutate_number`

修改技能已经存在的数字。

可以修改：

- 前摇时长。
- 冷却时长。
- 飞弹速度。
- 判定半径。
- 波前速度。
- 已配置的分裂数量。
- 已配置的持续时间。

不能凭空发明一个技能原本没有的字段。

## 15.2 `add_behavior`

给技能增加原本没有的行为。

例如：

- 原本命中即消失的飞弹获得穿透。
- 原本单体的飞弹获得分裂。
- 原本没有结束派生的区域获得到期爆炸。

增加行为后，行为中出现的数字才可能成为后续可修改字段。

## 15.3 `mutate_live_instance`

修改场上已经存在实例上、已经暴露的数字。

可以讨论：

- 飞弹已经在飞，速度发生改变。
- 火区已经存在，剩余有效时长发生改变。
- 环绕刃已经存在，半径发生改变。

不能：

- 改已经发生的 `hit`。
- 让已经飞出的普通飞弹突然凭空获得分裂行为。
- 通过改数字修改过去发生的轨迹和命中。

## 15.4 “接口”原则

没有对应字段，就不能假装修饰器生效；没有对应行为权限，就不能偷偷增加行为。

参考《流放之路》时，只借“词缀要声明落在哪一段”；参考《魔法工艺》时，只借“没有接口就接不上”；参考《骰子浪游者》时，只借“可以改已经存在、已经看见的数字”。不整套移植参考游戏规则。

<a id="第16章　场上实例与实时修改"></a>
# 第16章　场上实例与实时修改

## 16.1 过去不能被改写

事件已经发生后，修饰器不能回头改写：

- 已经结算的伤害。
- 已经发生的命中。
- 已经选择过的目标。
- 已经走过的路径。

实时修改只能作用于仍在场上、仍然暴露并允许被修改的数字。

## 16.2 推荐的实时数值处理

推荐从基准值重新计算，而不是按拾取顺序反复乘除：

```text
基础值
→ 收集当前仍有效的兼容修饰器
→ 按类别合并
→ 计算当前实例可见数值
```

这样更容易处理：

- 修饰器添加。
- 修饰器移除。
- 多件修饰器叠加。
- 场上多个实例同时更新。
- 不同来源的优先级。

这仍是推荐草案，不是最终数值系统。

## 16.3 实时增加行为的边界

当前推荐：

- `add_behavior` 影响之后生成或之后进入行为阶段的实例。
- `mutate_live_instance` 影响已经存在实例的已有数字。
- 两者组合不能默认让旧实例突然获得全新行为。

如果未来确实要做“场上所有飞弹立即分裂化”，应单独建立明确的迁移规则、父子关系和循环保护，不要把它伪装成普通实时改数。

<a id="第17章　持续效果的重施放与叠加"></a>
# 第17章　持续效果的重施放与叠加

## 17.1 不能用一个规则强套所有持续效果

飞弹、火区、环绕和持续射线的重施放目的不同。推荐按用途选择模板：

| 类型 | 推荐重施放方向 |
|---|---|
| 飞弹 | 每次生成独立实例 |
| 固定地面区域 | 有限叠加或按来源刷新 |
| 环绕刃 | 同组刷新或替换 |
| 持续射线 | 刷新、换方向或按技能声明叠加 |

“持续时间与冷却取较大值”不是当前正本规则，不能直接抄入。

## 17.2 持续伤害的目标间隔

推荐让不同类型使用不同默认：

- 火区：按效果体实例计，多个明确叠加的火区各自按自己的间隔结算。
- 同组环绕飞刃：共享对同一目标的结算间隔，避免多把飞刃同帧爆量。
- 特殊穿门或边缘技能：可用重新进入时判定，但不作为一般持续伤害默认。

这些是推荐草案，不是所有技能强制规则。

## 17.3 闪避不让持续区域消失

一次持续伤害尝试全部被闪避，只影响本次尝试：

- 不产生 `hit`。
- 不执行 `hit` 派生。
- 火区继续存活。
- 不在同帧无限重试。

# 第五部　技能文档的标准写法

<a id="第18章　玩家文字与设计文字"></a>
# 第18章　玩家文字与设计文字

## 18.1 玩家文字只写四类可见结果

玩家说明推荐聚焦：

1. 生成什么。
2. 怎么动。
3. 打中怎样。
4. 结束怎样。

例如：

> 射出一枚火炮弹，落地后留下燃烧区域，区域内的敌人会持续受到火焰伤害，持续一段时间后消散。

## 18.2 设计文字要写完整内部规则

设计文档必须补充：

- 施法者索敌和前摇。
- 出手时机。
- 载体类型。
- 效果体生命周期。
- `hit` 与 `vanish`。
- 终止原因。
- 派生条件。
- 每份伤害的闪避与减免。
- 修饰器能修改哪些字段。

玩家文字不写 `hit`、`vanish`、回收、层一、层二和修饰器权限名；设计文档不能因为追求易读就删除这些必要信息。

## 18.3 玩家属性区与效果正文分开

推荐把玩家界面分三层：

- 效果正文：只讲技能实际产生的可见效果。
- 属性区：展示冷却、连发次数、范围等玩家需要的数字。
- 详细或调试层：展示动作分组、逐份结算、修饰器来源和内部状态。

这不意味着冷却数值不能显示，而是不要把冷却写进四句效果正文。

<a id="第20章　其他-ai-应如何分析一个新技能"></a>
# 第20章　其他 AI 应如何分析一个新技能

## 20.1 第一步：先拆施法者和效果体

看到“施法者蓄力发射炮弹”时，先改写为：

```text
施法者：索敌 → 前摇 → 出手 → 冷却
炮弹：生成 → 抛射运动 → 落地终止 → vanish → 派生火区 → 回收
火区：生成 → 滞留 → 周期 hit → 到期终止 → 回收
```

不要把炮弹飞行和火区持续伤害塞回施法者链条。

## 20.2 第二步：确认载体

问“这段效果是否需要自己的存活过程”：

- 不需要：无载体。
- 施法者本人移动：自身载体。
- 另一个实例独立存在：独立载体。

## 20.3 第三步：确认事件入口

只允许检查：

- 是否由 `hit` 驱动。
- 是否由 `vanish` 驱动。
- 其他条件是 `hit` 上的条件，还是终止原因过滤。

## 20.4 第四步：确认单位

按顺序检查：

```text
施放轮次 → 动作 → 瞬时出手 → 攻击实例 → hit → hit 内伤害份
```

不要看到“多颗子弹”就说是多次出手；不要看到“多个数字”就说是多次命中。

## 20.5 第五步：确认终止原因

写清是：

- 命中后终止。
- 到达距离终止。
- 落地终止。
- 滞留到期终止。
- 正常回旋结束。
- 强制清场回收。

只有允许的正常终止才挂对应的 `vanish` 派生。

# 第21章　其他 AI 如何补齐未定细节

## 21.1 正确的问题格式

错误：

> 这个要怎么做？

正确：

> 这里有三个可执行方案。A 让整轮连发结束后再冷却，优点是动作组完整，代价是增加出手会拉长站桩；B 从首发开始并行冷却，优点是节奏紧凑，代价是冷却可能在连发中途结束；C 每个动作组单独起手，优点是重武器感强，代价是起手成本高。结合当前技能 DIY 方向，我推荐 A。双脉冲样例下表现为……

## 21.2 方案不宜堆砌

不是把每个细节都列成十几个微小选项，而是把互相依赖的细节组成一套完整方案：

- 连发前摇、出手间隔、冷却起点组成一组。
- 命中前状态、暴击、格挡和派生时机组成一组。
- 持续区域的重施放、叠加和目标间隔组成一组。
- 修饰器权限、生效对象和实时更新组成一组。

通常给 2—3 个真正不同的候选，并给出推荐。

## 21.3 不确定事实要标注

外部资料只能回答：

- 引擎有没有某项能力。
- 某个参考系统公开资料如何描述机制。
- 某种实现方式有哪些常见边界。

外部资料不能直接回答：

- 本项目一定要采用哪种玩法。
- 金弋顺已经批准了哪个方案。
- 尚未确认的最终数值是多少。

<a id="第22章　双脉冲射击六次出手样例"></a>
# 第22章　双脉冲射击：六次出手样例

## 22.1 样例定义

```text
动作一：出手① → 出手②
动作二：出手③ → 出手④
动作三：出手⑤ → 出手⑥
```

本例暂时假设每次出手生成一颗飞弹，只为了观察单位关系。

## 22.2 数量关系

- 整轮瞬时出手：六次。
- 动作：三个。
- 每个动作内先后出手：两次。
- 飞弹实例：六个。
- 最终 `hit`：不由六次出手直接保证，取决于命中。
- 每条 `hit` 的伤害份：另行描述。

如果一颗飞弹穿透三个敌人，它增加的是 `hit` 条数，不增加 X。

如果一次出手同时生成两颗飞弹，出手仍然只有一次，变化的是实例数量。

## 22.3 推荐的理解方式

先写完整中文过程句：

> 一轮先后完成六次瞬时出手，分为三个举杖动作，每个动作内先后出手两次；每次出手生成一颗独立飞弹。飞弹独立运动，命中按逐份闪避与伤害结算，是否穿透或分裂由实例规则决定。

暂时不要用 Y、Z 强行压缩，因为 Y、Z 的新分配还没有锁定。

<a id="第23章　瞬时近战扇形"></a>
# 第23章　瞬时近战扇形

## 玩家文字

> 挥击前方扇形区域内的敌人。

## 设计流程

```text
施法者：索敌／确认方向 → 可选前摇 → 瞬时出手 → 冷却
出手：在当前扇形范围内查找目标
目标：逐目标逐份判断闪避与伤害
```

它是无载体技能，不产生持续实例，也没有 `vanish`。

如果扇形内有三个目标：

- 三个目标分别检查。
- 每个目标可以形成自己的 `hit`。
- 三个目标不是一条 `hit` 内的三份伤害。
- 画面上一次挥刀，不代表整个区域只有一次命中事件。

如果要做“刀光从左向右扫过，先扫到的先受伤”，则需要把扫动声明为真实判定波前；仅仅播放一个从左到右的动画不够。

<a id="第24章　普通远程飞弹"></a>
# 第24章　普通远程飞弹

## 玩家文字

> 向目标射出一枚飞弹，命中后消散。

## 设计流程

```text
施法者：索敌 → 可选前摇 → 出手 → 冷却 → 回到索敌
飞弹：生成 → 直线／追踪运动 → 接触目标 → 逐份结算
      ├─ 全部伤害份闪避：无 hit，按飞弹自身规则继续或终止
      └─ 至少一份未闪避：一条 hit，按命中规则处理
      → 正常终止 → vanish（若本技能声明）→ 回收
```

“命中后消散”不是新增事件，而是飞弹在成立的 `hit` 后进入终止，并按规则发送 `vanish`。

如果增加穿透：飞弹命中后不终止，继续运行。

如果增加分裂：由 `hit` 派生新实例，父弹继续还是终止必须写明。

<a id="第25章　大炮抛射与地面持续火区"></a>
# 第25章　大炮抛射与地面持续火区

## 25.1 推荐结构

这是当前最完整、最适合可组合技能系统的推荐草案：

```text
施法者：索敌／选择地面落点 → 可选蓄力 → 瞬时出手 → 冷却
炮弹 A：生成 → 抛射运动 → 正常落地 → vanish → 派生火区 B → 回收
火区 B：生成 → 静止滞留 → 周期性范围判定 → 逐份闪避与伤害
         → 持续时间到期 → vanish（若需要结束派生）→ 回收
```

## 25.2 为什么是“落地终止”，不是“命中敌人后生成火区”

因为本例设计意图是“炮弹落到哪里，哪里留下火区”：

- 空地也应该留下火区。
- 炮弹落点有敌人但敌人全部闪避，火区仍应存在。
- 多个敌人在落点范围内，不应因为多个目标产生多片火区。
- 炮弹在空中被拦截，不应因为任意消失就生成火区。

因此，应该把“正常落地”作为终止原因和 `vanish` 派生条件，而不是把“敌人成功受击”作为留火条件。

## 25.3 火区的每次伤害

每到伤害时机：

1. 找当前范围内的合法目标。
2. 对每个目标单独组织本次伤害份。
3. 每份独立判断闪避。
4. 未闪避才计算该份伤害和适用减免。
5. 全部闪避则没有 `hit`。
6. 至少一份未闪避则产生该目标的一条 `hit`。
7. 处理该条 `hit` 的规则，等待下一次时机。

火区持续的是效果体存在，不是把一次伤害延长成一条无限大的 `hit`。

## 25.4 三个方案的比较

| 方案 | 说明 | 优点 | 代价 | 本例建议 |
|---|---|---|---|---|
| A | 炮弹正常落地后 `vanish` 派生独立火区 | 空地可留火，两个阶段边界清楚，适合修饰器 | 需要两个逻辑实例 | 推荐 |
| B | 炮弹成功 `hit` 后派生火区 | 适合“命中敌人才点燃” | 空地不留火，可能重复生成 | 不推荐用于本例 |
| C | 一个复合实例从飞弹切换成火区 | 固定组合实例少 | 切换判定、计时、修改边界复杂 | 可实现，不作为首选 |

## 25.5 终止原因表

| 炮弹结果 | 是否生成火区 |
|---|---|
| 正常落到合法地面 | 是 |
| 落到空地 | 是 |
| 落地范围内敌人全部闪避 | 是，闪避只影响伤害 |
| 空中被拦截 | 否 |
| 飞行寿命耗尽但没有落地 | 否，除非技能另有规则 |
| 强制清场／场景卸载 | 否，不发 `vanish` |

## 25.6 外部资料只支持实现可行性

Godot 官方 `Area2D` 文档说明，区域可以检测进入、离开并查询重叠对象；重叠列表按物理步更新，因此“创建火区后立即结算”在实现上需要注意物理同步，不能把底层重叠缓存直接等同于本系统 `hit`。

Godot 官方 `Timer` 文档说明，计时器到达等待时间后发出 `timeout`，可以作为周期调度手段；这个 `timeout` 是引擎实现信号，不是本项目新增的效果体事件。

Epic 官方 Gameplay Effects 文档区分了 Instant、Infinite、Has Duration 以及周期执行，这支持“持续时间”和“周期执行间隔”分开描述的设计参考，但不意味着本项目必须照搬 GAS。

<a id="第26章　冲刺跳跃与瞬移"></a>
# 第26章　冲刺、跳跃与瞬移

## 冲刺

- 载体：自身载体。
- 出手后施法者本人进入运动。
- 路径上可以发生 `hit`。
- 到达或按规则被打断后终止。
- 不能用极高移速把瞬移伪装成冲刺，反之亦然。

## 跳跃

- 载体：自身载体。
- 抛物线默认是表现。
- 当前工作口径：不越墙。
- 若中途被打断，不因动画结束就自动补落地伤害。
- 若想越墙，应提出独立规则，不能只把曲线画得更高。

## 瞬移

- 载体：无载体。
- 出手时直接修改坐标。
- 路径不产生命中。
- 落点爆炸应在同一次出手中生成独立爆炸实例。
- 不把瞬移写成“自身载体高速运动”。

<a id="第27章　穿透分裂弹射与连锁"></a>
# 第27章　穿透、分裂、弹射与连锁

## 穿透

同一实例命中后不终止，继续运动，可以再次命中。穿透不是派生。

## 分裂

由 `hit` 或 `vanish` 派生新实例。父实例是否继续，必须声明。

推荐写法：

```text
父弹命中甲 → hit 派生两颗子弹；父弹继续飞行
```

或：

```text
父弹命中甲 → hit 派生两颗子弹；父弹终止并发送 vanish
```

## 弹射

必须二选一：

- 同一实例命中后改变目标，继续生命周期。
- `hit` 派生新实例，父实例结束或继续由技能声明。

## 连锁

连锁与弹射同理。不要新增“连锁事件”。

推荐为同一条连锁路径保存访问历史和剩余派生额度，避免子实例重新从完整额度开始，造成无限链。

<a id="第28章　地震波地刺与环绕"></a>
# 第28章　地震波、地刺与环绕

## 地震波

- 载体：独立载体。
- 运动：判定半径从小到大扩张。
- 近处先被波前覆盖。
- 每个目标默认首次覆盖一次，是否重复由技能另写。
- 半径扩张不是新事件。

## 地刺列

两种模型都合法，但每个技能必须选一种：

1. 一个实例沿直线推进波前。
2. 一次出手生成多个实例，每个实例拥有开始延迟。

不能一半用波前、一半又把同一根刺说成新的出手。

## 环绕

- 载体：独立载体。
- 运动：绕施法者或指定中心运行。
- 不是角色每帧重新出手。
- 存活期间可以多次产生 `hit`。
- 重施放是叠加、刷新、替换还是禁止，需要按用途选择模板。

# 第七部　错误写法与验收

<a id="第29章　最容易犯的错误"></a>
# 第29章　最容易犯的错误

| 错误写法 | 错误原因 | 正确改法 |
|---|---|---|
| 施法者进入飞行阶段 | 飞行属于效果体 | 出手生成独立载体，飞行写在层二 |
| 攻击动作播完就是 `vanish` | 动画结束不是实例消失 | 只有技能实例终止并发送时才是 `vanish` |
| 每份伤害就是一条 `hit` | 一条 `hit` 可包含多份伤害 | 先确认是否产生了独立命中 |
| 所有伤害份都闪避也有 `hit` | 当前口径规定全部闪避无 `hit` | 无 `hit`，不执行命中派生 |
| 火区每跳都算角色重新出手 | 区域跳伤属于效果体 | 角色只出手一次，火区多次 `hit` |
| 炮弹只要消失就留下火区 | 空中销毁不等于正常落地 | 用终止原因过滤，仅正常落地留火 |
| 炮弹命中敌人才留下火区 | 不符合空地留火意图 | 落地 `vanish` 派生火区 |
| 用高速移动实现瞬移 | 会产生路径命中 | 瞬移无载体，直接改坐标 |
| 水晶把没有分裂的技能改成分裂 | 改数字不能新增行为 | 需要 `add_behavior` 或技能重配 |
| 遗物不能改场上数字 | 当前正本没有这个禁令 | 看是否开启 `mutate_live_instance` |
| 清场时补一个结束爆炸 | 清场不应制造攻击 | 不发 `vanish`，直接回收 |
| 顺时针贴图决定谁先受伤 | 表现不能自动变判定 | 若需扫过伤害，明确声明波前判定 |
| 给每次 X 出手都加完整前摇和冷却 | 多次出手编排不能机械复制单次模板 | 先定义整轮时序方案 |

<a id="第31章　给实现和测试的交接格式"></a>
# 第31章　给实现和测试的交接格式

## 31.1 设计交接句式

不要交接：

> 做一个大炮火球，落地后持续烧人。

应交接：

> 施法者在一次出手中固定地面落点并生成独立炮弹；炮弹正常落地时发送带“正常落地”原因的 `vanish`，由该 `vanish` 派生一个固定落点的独立火区。火区在自身有效期内按周期查找范围内目标；每个目标的每份伤害独立判闪避，未闪避才计算该份伤害与减免；全部份闪避无 `hit`，至少一份未闪避形成一条 `hit`。强制清场不发送 `vanish`，不留火区。

## 31.2 测试案例最少覆盖

### 正常路径

- 炮弹落在空地，火区生成。
- 炮弹落在敌人附近，敌人全部闪避，火区仍生成。
- 火区首次结算时有敌人，产生正确数量的目标级 `hit`。
- 火区中途进入敌人，后续伤害时机能够参与。
- 火区中途离开敌人，后续不再参与。

### 闪避路径

- 一份伤害被闪避，其他份正常结算。
- 全部份被闪避，不产生 `hit`。
- 未闪避但减免到 0，仍产生 `hit`。
- 不因部分闪避复制命中派生。

### 终止路径

- 正常落地留火。
- 空中拦截不留火。
- 强制清场不留火。
- 火区到期不额外跳伤。
- 火区有 `vanish` 派生时只在允许的正常到期路径触发。

### 数量路径

- 六次出手不被错误计成十二次。
- 一次出手三颗飞弹不被错误计成三次出手。
- 一颗穿透飞弹多次命中不增加 X。
- 一条 `hit` 三份伤害不被错误计成三条 `hit`。

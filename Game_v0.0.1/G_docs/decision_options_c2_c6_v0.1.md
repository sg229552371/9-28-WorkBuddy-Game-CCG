# Part A · C2 局内等级成长公式：加算 vs 乘算

> 对应设计书 §12 第 38 条（`game_design_proposal.md:1206`，**未拍板**）。
> 设计书 §8.5 原文：「该等级属性初始值 = 属性初始值 × 成长值 … `+1` 与乘算的具体衔接——加算还是乘算——见待细化 #38」（`game_design_proposal.md:878`）。

## A.0 现值实测后果（先摊开，**这是要被裁决的问题本体**）

现值 = **固定绝对增量**（每级给固定点数，**不随英雄初始值缩放**）：

| 通道 | hp/级 | atk/级 | def/级 | 位置 |
| ---- | ---- | ---- | ---- | ---- |
| A 等级直加 | +8 | +2 | +0 | `js/items.js:554`、`555`、`528`、`529` |
| B `baseStatGain` | +6 | +1.5 | +0.5 | `js/config.js:1717` → `js/items.js:501~507` |
| **合计** | **+14** | **+3.5** | **+0.5** | 上两行相加 |

现值折算成倍率后**随初始值剧烈漂移**（复用 B5 §1.4 实测表）：

| 参考英雄 | 属性 | Lv1 | Lv100（现值，绝对增量） | 现值倍率 | 结论 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| H001 猎手 | hp | 94 | 94 + 14×99 = **1480** | **15.7×** | 偏陡 |
| H001 猎手 | atk | 16 | 16 + 3.5×99 = **362.5** | **22.7×** | 偏陡 |
| H001 猎手 | def | 2 | 2 + 0.5×99 = **51.5** | **25.8×** | 偏陡 |
| H009 守护者 | hp | 155 | 155 + 14×99 = **1541** | **9.9×** | 偏平 |
| H009 守护者 | atk | 8 | 8 + 3.5×99 = **354.5** | **44.3×** | 严重偏陡 |
| H009 守护者 | def | 8 | 8 + 0.5×99 = **57.5** | **7.2×** | 接近线性 |

- **实测结论（B5 §1.4）**：现值对**低初始值属性**（H009 攻击 8、H001 防御 2）放大到 **25×~44×**，对**高初始值属性**（H009 生命 155）仅 **9.9×** —— **绝对增量把「短板属性」过度补偿**，抹平角色定位差异（设计意图见 `game_design_proposal.md:630`）。
- **与敌人对照（本次实测）**：敌人同等级系数 `1+(lv−1)×0.12`（`js/game.js:731`）→ **Lv100 = 12.88×**。现值下英雄（15.7×~44.3×）**远强于敌人**；这是「后期裸属性碾压」的量化来源。

> 结论：现值 = 「加算」的**退化解**（基数用了固定点数而非初始值）。下面三案都是在保留「加算/乘算」结构的前提下，**把成长基数改回「按初始值比例」**后做的对比。

## A.1 三个方案对比表（倍率两端点均对齐 Lv100 = 6.94×，便于同框比较）

统一口径：`M(lv)` = 「该等级属性 ÷ Lv1 初始属性」的**倍率**（对 hp/atk/def 各属性、各英雄通用）。
复用 B5 §1.1~§1.2：`r = 0.06`（= `CFG.skillScaleBy.levelGrowth`，`js/config.js:1307`）。

| 方案 | 公式（M(lv) = 倍率） | Lv1 | Lv10 | Lv30 | Lv50 | Lv100 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| **① 纯加算（按初始值比例·线性）** | `1 + 0.06×(lv−1)` | 1.00 | **1.54** | **2.74** | **3.94** | 6.94 |
| **② 纯乘算（几何）** | `k^(lv−1)`，`k = 6.94^(1/99) ≈ 1.01976` | 1.00 | **1.19** | **1.76** | **2.61** | 6.94 |
| **③ 混合（前 30 级加算、30 级后转乘算）** | lv≤30：`1+0.06×(lv−1)`；lv>30：`2.74 × k2^(lv−30)`，`k2 = (6.94/2.74)^(1/70) ≈ 1.01337` | 1.00 | **1.54** | **2.74** | **3.57** | 6.94 |
| —— 参照：现值（绝对增量） | 无统一倍率（随初始值漂移） | 1.00 | 漂移 | 漂移 | 漂移 | 15.7×~44.3× |
| —— 参照：敌人同等级 | `1 + 0.12×(lv−1)` | 1.00 | 2.08 | 4.48 | 6.88 | **12.88** |

**曲线形态（一句话）**：
- ①加算：**前期抬升猛、后段放缓**（Lv10 已 1.54×，中期很快给足）。
- ②乘算：**前期极平、末段陡升**（Lv50 才 2.61×，靠最后 20 级冲）。
- ③混合：**前 30 级与①完全一致（保住开局手感），30 级后切换为②的平缓外推**，两端点与①②同值。
- 三案的手感**唯一真正分野在 Lv10~Lv60 的中场**（B5 §1.2 已验证：Lv50 处 ①②差最大 = 1.33×）。

## A.2 各方案详述

### 方案 ① 纯加算（按初始值比例·线性）—— `M = 1 + 0.06×(lv−1)`

- **对英雄 vs 敌人的强弱关系**：英雄 Lv100 = 6.94× vs 敌人 Lv100 = 12.88× → **同等级裸属性英雄弱于敌人**（约 54%）。中场：Lv10 英雄 1.54× vs 敌人 2.08×。**英雄的差距只能靠武器栏装备 / 遗迹秘宝 / 雕像 Buff / 技能与 `baseStats` 折算补齐**。
- **对现有关卡 `hpMul` 曲线的兼容性**：关卡 `hpMul`（`js/config.js:2298~2323`）与敌人等级系数同源（`2310~2311` 注释）。加算曲线**与同源线性惯例一致**（敌人 12%/级、`CFG.outLevel.growth` 线性 `js/config.js:2088`），**「同一游戏一套线性成长哲学」**。唯一需拍板的是**英雄 6%/级 vs 敌人 12%/级 的落差分**（见 A.3）。
- **实现改动面（要动哪些文件/函数）**：
  - `js/config.js:1717`：`baseStatGain` 由「固定绝对值」改为「成长率」参数（或新增 `CFG.levelUp.growth = { mode:"add", rate:0.06, stats:["hp","atk","def"], base:"heroInit" }`）。
  - `js/items.js:500~507`（`runBonus`）：`baseStatGain` 的绝对增量循环 → 改读成长率。
  - `js/items.js:554`、`555`（`computeStats`）与 `528`、`529`（`companionStats`）：`+8*n` / `+2*n` 改为 `初始值 × 0.06 × n`（def 补上等级项）。
  - 回归测试：`exp_test.js:106~108`、`smoke_test.js:152`、`perf_test.js:224`（后者手写了 `100 + 8*n + …` 口径）。
- **风险**：低。**唯一风险 = 若不同步调整敌人侧/装备侧强度，中期（Lv10~30 英雄 1.54~2.74× vs 敌人 2.08~4.48×）会出现「英雄越打越吃力」的压迫感**。

### 方案 ② 纯乘算（几何）—— `M = k^(lv−1)`，`k ≈ 1.01976`

- **对英雄 vs 敌人的强弱关系**：端点同为 6.94× vs 12.88× → 同①；但**中前期英雄明显更弱**（Lv10 仅 1.19×、Lv30 仅 1.76×），Lv50 之后才追上①。**中期压迫感最强**。
- **对现有关卡 `hpMul` 曲线的兼容性**：**不兼容现有线性惯例**。敌人与 `outLevel` 成长都是线性/分段（加算），本作仅技能等级走「等价 6%/级」但没有真正的几何外推。乘算会引入**第三套成长哲学**。若 `k` 按技能同源的 `1.06` 取，Lv99 达 `1.06^98 ≈ 312×`（B5 §1.3 数值爆炸）；必须压到 `≈1.01976` 才可控 —— 而压平后与①的差异**仅中场 1.33× 量级**，收益有限。
- **实现改动面**：同①（改 `config.js:1717` + `items.js` 三处），但公式写法为 `初始值 × k^(n)`，需注意**取整与浮点累积**（B5 §1.4 已提示会破坏跨英雄一致性）。
- **风险**：中高。①几何外推失控（若策划误填 `k`）；②中前期过平导致「升级无感」；③与现有一切线性系统口径割裂；④浮点误差随等级放大。

### 方案 ③ 混合（前 30 级加算、30 级后转乘算）—— 分段两段式

- **公式**：`lv ≤ 30`：`M = 1 + 0.06×(lv−1)`；`lv > 30`：`M = 2.74 × 1.01337^(lv−30)`，保证 `M(100) = 6.94`。
- **对英雄 vs 敌人的强弱关系**：端点与①②一致（6.94× vs 12.88×）。**前中期完全等于①（保住开局手感），后段收敛到②的平缓形态**；Lv50 = 3.57×，介于①②之间（比加算低 0.37×、比乘算高 0.96×）。
- **对现有关卡 `hpMul` 曲线的兼容性**：**前 30 级兼容最好（与①同），后段偏离线性**；适合「前期关卡（1~30 关）曲线线性、后期关卡（31~99 关）转陡」的未来规划，但**当前 `hpMul` 表仅覆盖到 lv20（`js/config.js:2323`）**，31 关后的曲线尚未定义 → **需与关卡侧一并对齐，耦合度最高**。
- **实现改动面**：比①②多一个**分段分支**——需在 `js/config.js:1717` 附近新增 `segments`（切换等级 N=30、两段系数），并在 `js/items.js:500~507` / `554,555` / `528,529` 里按 `lv` 分支。
- **风险**：中。①**两套手感在同一局内切换（Lv30 前后）易被玩家察觉**（"中期突然变慢"）；②分段点 N 与后期关卡 `hpMul` 需要同时定，**任一方改动都会破坏另一方的平衡**；③代码分支增加，测试面更大。

## A.3 关键耦合：英雄成长率 6%（本项）vs 敌人 12%（`js/game.js:731`）

- 敌人 Lv100 = 12.88×、英雄三案 Lv100 = 6.94× → **英雄裸属性成长率只有敌人一半**。
- 现值（15.7×~44.3×）则**反超敌人**。**本次拍板把英雄从「远强于敌人」翻转到「裸属性弱于敌人」**，这个翻转是**有意的**（B5 §1.4 已把这个强弱锚明示为「需与关卡 `hpMul` 曲线一并拍板」）。
- 两种收口方式（**本项拍板后需紧跟一轮「强弱锚」决策，不在本文件拍**）：
  - **A3-α（推荐）**：英雄保持 6%/级，**英雄战力由装备 / 遗迹秘宝 / 雕像 Buff / 技能 / `baseStats` 折算承担**，敌人保持 12%/级。→ 鼓励搜刮与构筑（符合「搜打撤 + 背包 Roguelike」核心）。
  - **A3-β**：把英雄成长率提到 12%/级对齐敌人（则 `M(100) = 12.88×`，与技能 `skillScaleBy.levelGrowth = 0.06` **不再同源**，需另立系数）。

## A.4 推荐

> **推荐：方案 ① 纯加算（按初始值比例·线性 `1 + 0.06×(lv−1)`）。**

理由（每条一句）：
1. **同源零新增口径**：`r = 0.06` 直接复用 `CFG.skillScaleBy.levelGrowth`（`js/config.js:1307`），技能与英雄两条曲线共用同一数字，无需维护第二套系数。
2. **与全项目线性惯例一致**：敌人 `1+(lv−1)×0.12`（`js/game.js:731`）、局外成长 `CFG.outLevel.growth`（`js/config.js:2088`）都是加算；乘算会引入第九/第三套成长哲学。
3. **消除现值漂移**：把基数从「固定绝对增量」改为「初始值 × 比例」，直接消灭 A.0 的 25×~44× 短板放大异常，恢复角色定位差异。
4. **实现改动面最小**（仅 1 个配置项 + 3 处函数），且**风险最低**；②③的收益（中场手感差异 1.33×）不足以承担几何外推/分段切换的额外风险与耦合。
5. **前 30 级手感与③相同**——若未来需要后段收敛，可**先落①、后续再按段扩展③**，是**风险最低的渐进路径**（③作为①的超集）。

> ⚠️ 推荐①**不等于**推荐「英雄 6% vs 敌人 12% 的强弱锚」（那是 A.3 的独立决策）；本项只裁决**公式形态**。

## B.4 各方案详述

### 方案 ① 彻底退役（以遗迹秘宝 / 模块槽替代）——**与现状「半退役」最一致**

- **理由链**：卡牌的三个职能**已各有归属**——「升级加属性」→ `CFG.levelUp.baseStatGain`（`js/config.js:1717`，`game_design_proposal.md:2500~2502`）；「4 档品质构筑」→ `CFG.chips` 遗迹秘宝（`js/config.js:1775`，`game_design_proposal.md:2116`）；「个人技能构筑」→ 能量水晶（`game_design_proposal.md:2942`）。
- **只需「把已经断掉的入口正式确认 + 补做物理清理」**，不需要回滚任何已砍链路。
- **风险最低**：唯一代价是玩家少一层「攒卡—兑现」的延迟满足；缓解手段 = 遗迹秘宝的「宝箱获取 → 遗迹工坊合成/重铸」已提供同类循环（`game_design_proposal.md:2806~2807`）。

### 方案 ② 恢复卡池（按 §12-27 建 4 品质卡表）

- **必须整体回滚**已砍的链路（发卡 / 页签 / 按钮 / 通道 / 测试），且**要为 §12-27 填出完整的 4 品质卡池数值与权重**（当前 `CFG.cardPool.attrs` 只是 9 属性 × 4 档的**雏形**，`js/config.js:2127~2137`，未含 §8.3 所列「攻速 / 弹道数量等」的完整卡池）。
- **风险最高**：与遗迹秘宝（全队 4 品质）+ 能量水晶（个人技能）**三重叠加**；且第 3 代水晶系统刚拍板为「技能侧唯一方向」（`game_design_proposal.md:2948`），恢复卡牌存在**方向冲突**。
- **适用前提**：只有当用户明确希望「局内多一层属性卡资源管理」且**愿意砍掉遗迹秘宝或水晶其中之一**以避免叠加时，才建议选②。

### 方案 ③ 混合（只保留「工匠世界属性增益」形态）

- 即：**保留 §8.3 的「卡牌效果 = 强化角色属性」**（`game_design_proposal.md:817`），**砍掉**「升级攒资产 / 候选 4 选 1 / 刷新按钮」（§12-27/37 的卡池与经济）。
- 玩家在工匠世界可**直接选择一次属性增益**（复用 `CFG.cardPool.attrs` 的 9 属性 × 4 品质数值），相当于把卡牌降级为「一次性属性 Buff 选择」。
- **风险**：与 `baseStatGain`（升级即时属性）**功能重叠**，玩家难以区分两个属性来源；且仍需维护卡表数值。**收益（一层选择交互）不足以抵消重叠成本**。

## B.5 推荐

> **推荐：方案 ① 彻底退役。**

理由（每条一句）：
1. **职能已被完全覆盖**：升级属性（`baseStatGain`）+ 全队 4 品质构筑（遗迹秘宝）+ 个人技能构筑（能量水晶）三足鼎立，卡牌**无处安放**。
2. **与代码现状最一致**：卡牌**入口已断、页签已删、发卡已停**（`index.html:368`、`js/main.js:343~353/435`、`js/game.js:82`），选① = **确认既成事实 + 补物理清理**，无需回滚任何东西。
3. **方向一致**：§20 明定「技能侧唯一方向」（`game_design_proposal.md:2948`），卡牌不在其中；§19.7 已判删除（`2557`）。
4. **风险与工期最优**：不扩大首版范围（首版清单 `game_design_proposal.md:2166~2178` 本无卡牌）。
5. **②③ 的核心代价**（三重叠加 / 功能重叠）**都高于其收益**。

> ⚠️ 选①**必须同时补做物理清理**，否则「标了 `removed` 但 `runBonus/tagCalc` 仍读 `appliedCards`」的**半退役态会长期留在代码里**，成为隐性坑（本次实测已发现该不精确表述，见 B.2）。

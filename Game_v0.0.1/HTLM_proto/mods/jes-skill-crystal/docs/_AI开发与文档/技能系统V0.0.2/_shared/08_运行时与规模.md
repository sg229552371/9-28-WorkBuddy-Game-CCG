# 第14章　运行时规则：固定步长、同帧顺序、FIFO、RNG、重复命中、目标死亡

> 一句话结论：技能系统以固定步长 tick 为唯一时间基准；同一 tick 内事件先进先出、同级按实例创建序号 `seq` 稳定排序；本 tick 派生的子实例下一 tick 才能命中；死亡目标不再产生 hit；闪避等随机判定走可注入的种子 RNG。本章全部为 v0.2 新补定义。

## 14.1 固定步长 tick 是时间基准

1. 技能系统的一切时间量（`lifetime_ticks`、前摇、冷却、开始延迟、`rehit_interval_ticks`、波前速度）都以 **tick** 计，不以真实秒或渲染帧计〔D-30 推荐默认〕。
2. 设计卡可以写“秒”作为人读单位，但必须同时给出换算后的 tick 数，或声明“秒 × tick 频率，向上取整”。取整方向要写明，默认向上取整〔D-30 推荐默认〕。
3. 渲染帧率与 tick 解耦：一个渲染帧内可执行 0、1 或多个 tick；渲染层用插值显示，不改变逻辑结果。
4. 一个 tick 内的处理阶段顺序（推荐，供实现对照）〔D-30 推荐默认〕：

| 阶段 | 内容 |
|---|---|
| ① 输入/出手 | 施法者闭环推进：到时间表的出手点则创建实例 |
| ② 运动 | 所有 `live` 实例按 `seq` 推进位置/半径/等待计时 |
| ③ 接触收集 | 收集候选接触（只含“可命中”的实例，见 14.4） |
| ④ 结算 | 按 14.3 的顺序逐条走第11章，发 hit，写结算记录 |
| ⑤ 终止与派生 | 处理 vanish、派生；新实例入队，下一 tick 才可命中 |
| ⑥ 回收 | `terminating` → `gone`，释放预算 |

## 14.2 暂停与慢动作

1. 暂停：tick 不推进，所有持续时间与冷却冻结。
2. 慢动作/加速：通过**统一的时间缩放因子**改变“每真实秒推进多少 tick”，而不是修改各实例的 tick 数。持续时间与冷却因此统一缩放，不会出现“冷却走真实时间、持续时间走缩放时间”的错位〔D-31 推荐默认〕。
3. 不在技能层引入第二个缩放系数。若某技能想“不受慢动作影响”，须在设计卡声明，并列入待上报评估；默认不允许。
4. 外部做法参考：Godot 的 Timer 受 `Engine.time_scale` 影响（除非 ignore_time_scale），且处理可能依赖帧率或 `physics_ticks_per_second`，到点发 `timeout`——外部事实（2026-10-17 抓取），E6 Godot Timer，https://docs.godotengine.org/en/stable/classes/class_timer.html 。本书据此要求：技能计时不用引擎 Timer 的真实时间语义，而用本章的 tick 计数，避免帧率相关的差异。
5. 快速模式下一帧执行多个 tick 时，每个 tick 完整走 14.1 的六个阶段，不得合并或跳过。

## 14.3 事件 FIFO 与同 tick 稳定排序

1. 事件只有 `hit`、`vanish`。事件进入一个全局 FIFO 队列，先产生先处理〔D-32 推荐默认〕。
2. 同一 tick 内多个候选接触的结算顺序：
   - 第一键：实例 `seq`（创建序号）升序；
   - 第二键：同一实例内，目标按稳定标识（如 `target_id` 升序）；
   - 不使用哈希表遍历顺序、对象内存地址、距离浮点比较结果（距离需要先后时，用波前，第12章）；位置比较用容差时，容差内平局按 `target_id` 升序定序。
3. `seq` 全局单调递增，由创建时分配，永不复用〔D-32 推荐默认〕。派生体的 `seq` 大于父实例。
4. 同一实例上，hit 先于 vanish：例如瞬时实例的全部候选接触结算完后才发 `instant_end` 的 vanish（12.2）。
5. 同一 tick 内处理一个事件时产生的新事件追加到队尾，不插队、不递归深入处理。这样事件处理深度恒定，不会因派生链造成栈增长。
6. 结算记录（`hit_settled`、`evaded_all`、`damage_taken`、`cast_started`）在对应结算完成后立即写入，被动触发层读取（第21章），读取到的是已排序的稳定序列。
7. 状态变化（无敌、死亡、冷却）在处理某事件时被修改，对**之后**出队的事件生效，不回溯已结算的事件〔D-32 推荐默认〕。

## 14.4 本 tick 派生的子实例下一 tick 才可命中

1. 在 hit 或 vanish 上派生出的子实例，创建于本 tick 的阶段 ⑤，其 `spawn_tick` 为本 tick；**首次可参与接触收集的 tick 为 `spawn_tick + 1`**〔D-33 推荐默认〕。
2. 理由：避免同一 tick 内无限链式命中（命中→派生→立刻命中→派生…），使每个 tick 的工作量有上界；与第20章的派生代数限制互补。
3. 瞬时实例例外：它本身就是“在创建的那个 tick 内完成判定”。区别在于：由**出手**创建的瞬时实例在阶段 ① 创建，当 tick 阶段 ③ 就参与接触；由**派生**创建的瞬时实例在阶段 ⑤ 创建，遵循本条，下一 tick 才判定〔D-33 推荐默认〕。
4. 子实例的开始延迟（12.4）从其首个可参与 tick 起算。

## 14.5 已死目标不再产生 hit

1. 同一 tick 内，目标已被先出队的 hit 结算至 `killed=true` 后，后续对该目标的候选接触**不再产生 hit**，也不记 `evaded_all`〔D-34 推荐默认〕。
2. 目标死亡以“结算完成时刻”为界。同一条 hit 内的多份伤害不会被中途截断（一条 hit 内的各份一并结算）。
3. 过量伤害不转嫁：未命中的接触不会因目标已死而改指同组其他目标，除非该实例自己的运动规则（追踪/弹射/连锁）在下一 tick 重新选目标。
4. `hit_settled` 的 `killed` 标记用于被动触发层判断“击杀”，不引入第三个事件。
5. 已死目标不再产生候选接触（14.7），因此不计入 `per_target_limit` 与 rehit 计时（复活规则不在本书范围）。

## 14.6 种子化可注入 RNG

1. 所有随机判定（逐份闪避、暴击若采用、随机选目标）都从一个**可注入的、带种子的 RNG 接口**取值；技能系统内部不得直接调用全局随机〔D-35 推荐默认〕。
2. 抽取顺序由 14.3 的排序决定：先按 `seq`，再按目标，再按 `part_index`。同样的输入与同样的种子必须得到同样的闪避结果。
3. 无敌目标的所有份在步骤 1 直接视为闪避，**不消耗 RNG 抽取**（见 11.4）；这样“同一场战斗是否对某目标无敌”不会令其他目标的随机序列错位。**每次候选接触（14.7）只做一次逐份闪避判定**，全闪避后不得在后续 tick 对同一次候选接触重掷；下一次重新判定只能来自新的候选接触（再次进入重叠，或 `rehit_interval_ticks` 到点）〔D-35 推荐默认；R2〕。
4. 每次抽取的用途标记（如 `evade`、`crit`）用于调试，不影响数值。
5. 测试时注入固定序列（例如恒为“闪避”或恒为“不闪避”），即可对第11章所有分支写出稳定的验收例子。
6. 表现层的随机（粒子抖动、屏幕震动）使用**另一个独立 RNG**，不得消耗逻辑 RNG〔D-35 推荐默认〕。

## 14.7 重复命中默认与声明

契约冻结的 `hit_policy`：`per_target_limit`（默认 1）、`rehit_interval_ticks`（可选）、`max_hits`（可选）。

| 情形 | 默认 | 须声明 |
|---|---|---|
| 普通飞弹、爆炸 | 每实例每目标 1 次（`per_target_limit=1`） | 无 |
| 穿透飞弹 | 对不同目标各 1 次；穿透额度用尽发 `hit_end` | 穿透额度（`max_hits`） |
| 持续火区 | 不能默认重复 | **必须**声明 `rehit_interval_ticks`；可选 `max_hits` |
| 环绕体 | 不能默认重复 | **必须**声明 `rehit_interval_ticks`（可声明组共享） |
| 回旋体（去程回程） | 默认每目标 1 次 | 回程可再次命中则须声明 `per_target_limit=2` 或 `rehit_interval_ticks` |
| 波前 | 默认每目标 1 次 | 见 12.3 |

**候选接触**〔D-36 推荐默认；R2 裁决〕：实例与目标由不重叠变为重叠（进入），或 `rehit_interval_ticks` 到点（目标仍在范围内），各算**一次**候选接触。每次候选接触只走一次第11章结算（逐份闪避只判一次）。无论该次结算是否成立 hit（含全闪避、含无敌），都算一次候选接触。

规则〔D-36 推荐默认〕：

1. 默认值是“每实例每目标 1 次”。需要超过 1 次必须在设计卡显式声明，缺省视为设计缺陷。
2. 计数对象是**实例**，不是技能或施法者：两个火区实例各自独立计数，是否合并见第19章。
3. `per_target_limit` 按**候选接触**计，无论是否成立 hit（含全闪避、无敌）；全闪避也消耗一次额度，否则会逐 tick 重掷闪避（11.4、14.6）。火区靠 `rehit_interval_ticks` 到点产生新的候选接触，不受 `per_target_limit=1` 的影响（声明了 rehit 的实例，额度语义见设计卡）。
4. `rehit_interval_ticks` 从上一次**候选接触**的 tick 起算（无论成立与否）；这与“火区不在同一 tick 重试”配合：一个判定时机一次候选接触、一次闪避判定。
5. `max_hits` 为实例总命中上限（跨目标累计），**只计成立的 hit**，全闪避不计；用尽发 `hit_end`（契约原因码表）。家族登记（防分裂体二次命中，第20、30章）按“已发生的候选接触”登记。
6. 同时声明 `per_target_limit` 与 `rehit_interval_ticks` 时，两者都须满足才可命中。

## 14.8 防霰弹：同次出手多实例对同一目标

**问题**：齐发（10.3）的三个飞弹同 tick 打中同一个大目标，会出现三条 hit，使“多弹”远强于设计预期。

外部做法参考：PoE 的投射物规则里，同时生成的多个投射物对同一目标只有一个能碰撞——外部事实（2026-10-17 抓取），E1 PoE wiki「Projectile」，https://www.poewiki.net/wiki/Projectile 。本书只借用“防霰弹”这个概念，是否采用及具体口径如下，是候选。

| 候选 | 规则 | 体验 | 优点 | 代价 | 典型案例 | 与已确认规则兼容性 |
|---|---|---|---|---|---|---|
| A 默认防霰弹 | 同一 `origin_cast_id` 同一出手点生成的多个实例，**同一 tick 内**对同一目标默认只有一个（按 14.3 顺序最先结算者，即 `seq` 最小）能命中 | 多弹用于覆盖面与扩散，不用于近距离叠伤 | 抑制近身倍增；伤害上限可预测；减少同 tick 的 hit 数 | 近距离多弹不再强；需要“霰弹”爽感的技能须显式关闭 | 三叉飞弹、扇形多箭 | 兼容 D-01（只改命中判定，不新增事件） |
| B　不防 | 每个实例独立命中 | 近身倍增，爽快 | 规则最简单 | 伤害失控；同 tick 同目标多条 hit，规模压力大 | 霰弹枪 | 兼容，但与 D-03 规模目标相冲突 |
| C　按技能声明 | 无默认，每个技能自行声明 | 灵活 | 设计者控制 | 容易遗漏，AI 补齐时常漏写 | — | 兼容，但违背“最小默认值” |

**推荐：A**，并提供设计卡开关 `shotgun_allowed`（默认 false）〔D-37 推荐默认；是否采用可由用户推翻〕。理由：D-03 的规模目标要求限制同 tick 同目标的 hit 数；设计者要“霰弹感”时显式打开即可。

**适用范围**〔R12 裁决〕：防霰弹只管“同一次出手同时生成的**独立实例**之间”。派生体与父体、分裂体与母体之间**不**用防霰弹，而用“家族登记”（按已发生的候选接触登记，见第20、30章）；两者是不同机制，不得混称。

实现口径（规则，不写代码）：

1. “同次出手同时生成”＝同一 `origin_cast_id` 且同一出手点且 `spawn_tick` 相同。
2. 被抑制的实例对该目标视为**不构成候选接触**（不是闪避，不记 `evaded_all`，不消耗 `per_target_limit`），可继续飞行并命中其他目标。
3. 谁是“能命中的那一个”：本 tick 内按 14.3 顺序最先结算的那一个（即 `seq` 最小者）。抑制窗口仅限**同一 tick**；次 tick 起，未被抑制的实例各自独立判定（2026-10-18 小修 6a/6b）。
4. 不同出手点（连发的第 1 次与第 2 次）互不抑制。
5. 派生体与父体、分裂体与母体不在防霰弹范围内，由家族登记管理（第20、30章）；同一次 hit 派生出的多个子实例之间如何避免同时命中同一目标，也由家族登记处理，不用防霰弹一词。
6. 若“能命中的那一个”被全闪避，同批其余实例**仍保持被抑制**（整批共用一次闪避判定；省 RNG，语义为“这批这次没打中”）。要“多弹至少中一发”手感的技能，用 `shotgun_allowed=true`〔2026-10-18 小修 6c，推荐默认〕。

## 14.9 确定性（D-09 已确认）

〔D-09 已确认（2026-10-18）〕：技能运行时采用固定步长 + 可注入种子 RNG，保证同一输入与种子逐次运行结果一致。**不做联网同步**是范围边界（本书不涉及），不属于 D-09 的确认内容。

为什么固定步长：

1. 外部事实（2026-10-17 抓取），E7 Glenn Fiedler「Fix Your Timestep」，https://gafferongames.com/post/fix_your_timestep/ ：固定 dt + 累加器使模拟与渲染帧率解耦，可得到逐次运行完全一致的结果（适用于确定性锁步）；半固定步长因浮点精度不完全一致；渲染用 alpha=累加器/dt 插值。本书因此采用固定步长，不采用半固定/可变步长。
2. 外部事实（2026-10-17 抓取），E5 Godot Area2D，https://docs.godotengine.org/en/stable/classes/class_area2d.html ：`get_overlapping_*` 列表在物理步中更新一次，而非物体移动后立刻更新，文档建议改用信号。含义：引擎的重叠列表有“一步滞后”，本书把接触收集固定在 tick 的阶段 ③，并明确子实例下一 tick 才命中（14.4），与这种滞后一致，而不依赖引擎重叠列表的即时性。
3. 外部事实（2026-10-17 抓取），E6 Godot Timer：Timer 受 `Engine.time_scale` 影响且依赖帧率或 `physics_ticks_per_second`（见 14.2）。故技能计时用 tick 计数而非 Timer 的真实时间。

确定性边界：

| 项 | 本书口径 |
|---|---|
| 同输入同种子同结果 | 要求（单机回放、自动测试、复盘） |
| 联网锁步/回滚同步 | **不做**，不承诺跨机器浮点一致 |
| 浮点 | 不承诺跨平台位级一致；位置比较用容差，不用浮点相等判定顺序；**容差内平局按 `target_id` 升序定序**（14.3 第二键用稳定标识） |
| 渲染 | 不参与逻辑，只读 |

D-09 已确认，“逐次运行一致”的验收承诺与 14.6 的测试注入承诺均生效。若日后用户推翻 D-09：14.1 之外的规则（FIFO、`seq` 排序、下一 tick 命中、防霰弹）仍可保留，只放弃这两项承诺。

## 14.10 运行时规则的可测试性清单

| 规则 | 一条可观察断言（示例） |
|---|---|
| 14.1 tick 基准 | 渲染帧率 30/60/144 时，同种子下 hit 的 `tick` 序列相同 |
| 14.2 缩放 | 时间缩放 0.5 时，持续 60 tick 的火区仍发 60 tick 后的 `expired`，真实时长翻倍 |
| 14.3 排序 | 两个同 tick 命中同一目标的实例，`seq` 小者的 hit 先于 `seq` 大者出队 |
| 14.4 下一 tick | hit 派生的子实例，其首个 hit 的 `tick` ≥ 父 hit `tick` + 1 |
| 14.5 死亡 | 目标被先出队 hit 杀死后，同 tick 后续接触不产生 hit |
| 14.6 RNG | 注入“恒闪避”序列时，所有逐份判定为闪避；无敌目标不消耗抽取 |
| 14.7 重复命中 | 未声明 `rehit_interval_ticks` 的火区对同一目标最多 1 条 hit（应被审查为设计缺陷） |
| 14.8 防霰弹 | 三叉飞弹同 tick 打同一目标，默认仅 1 条 hit，另两个实例对该目标不构成候选接触 |

## 常见误写→正确写法

| 常见误写 | 正确写法 |
|---|---|
| "持续 2 秒" | "持续 120 tick（示例，秒×频率向上取整）" |
| "用引擎 Timer 计冷却" | 用 tick 计数；Timer 的真实时间语义不可靠（E6） |
| "命中后子弹立刻在当 tick 命中别人" | 子实例下一 tick 才可命中（14.4） |
| "遍历字典顺序结算" | 按 `seq`、`target_id` 稳定排序 |
| "死亡后同 tick 仍打出一条 0 伤害 hit" | 死亡目标不再产生 hit |
| "火区不写间隔，默认每帧打" | 火区必须声明 `rehit_interval_ticks` |
| "三个齐发飞弹各自命中同一目标，伤害翻三倍" | 默认防霰弹只一个命中；要霰弹感则 `shotgun_allowed=true` |
| "联网也保证一致" | 本书不做联网同步（范围边界；D-09 只确认单机确定性） |

# 第15章　规模：实例预算、碰撞分桶、超限丢弃、伤害数字合并

> 一句话结论：目标规模是同屏几百到 1000+ 个实例〔D-03 已确认〕；用分级预算限制总量，用碰撞分桶限制接触检测的候选对数，超限时先丢纯表现实例、判定实例最后丢，且全部丢弃行为必须是可观察、可测试的规则；伤害数字合并只影响显示，不影响结算。

## 15.1 规模目标

| 项 | 口径 |
|---|---|
| 同屏实例量 | 几百到 1000+ 个实例同时存在〔D-03 已确认〕 |
| 数字 | 此量级是设计目标，不是性能承诺；具体上限数值待性能测量后在附录/验收中填，本章只定口径与行为。**与项目性能基线的换算不属于本书范围**（2026-10-18 第四轮）：见项目层《性能口径换算_项目层_v0.1.md》，本书验收例子表不验证性能 |
| 示例数值 | 本章出现的数值（如 1200、30%）均为**示例**，不是最终配置 |

## 15.2 实例预算分级

每个实例在创建时归入一个预算类别。类别越靠后，超限时越先被丢弃〔D-38 推荐默认〕：

| 优先级 | 类别 | 含义 | 举例 | 超限时 |
|---|---|---|---|---|
| P0 | 玩家本人关键判定 | 玩家施放的、造成/防御关键效果的判定实例 | 玩家主炮弹、护盾、治疗 | 最后丢；不丢弃已存在者，满额时拒绝创建（15.4） |
| P1 | 敌方关键判定 | 影响玩家生死的敌方判定实例 | Boss 弹幕、致命区域 | 同 P0（15.4），拒绝顺序次后 |
| P2 | 普通判定实例 | 其他有判定的实例 | 小怪弹幕、普通火区 | 不丢弃已存在的根判定实例，满额时拒绝创建新的（15.4） |
| P3 | 派生体（带判定） | 命中/消失派生出的子实例 | 分裂体、爆炸余波 | 判定类里最先被拒绝创建、最先被丢弃（15.4、第20章派生预算） |
| P4 | 纯表现实例 | 无判定：拖尾、粒子、命中火花 | 火花、烟尘 | **最先丢** |

规则：

1. 纯表现实例**必须**能与判定实例分离为独立实例（9.4 第 4 条）；否则无法做到“先丢表现”。
2. 预算分三层：全局总量上限、每个施法者上限（召唤物受召唤上限约束，D-07 已确认，由第22章处理）、每类别上限。
3. 预算按**活着的实例**计（含等待期的实例，12.4 第 5 条；含 `terminating` 状态到 `gone` 之前）。
4. 瞬时实例按“本 tick 创建数”入预算，tick 结束即释放。

## 15.3 预算状态与可观察行为

用三档状态描述当前压力，行为可测试〔D-38 推荐默认〕（阈值为示例）：

| 状态 | 进入条件（示例） | 可观察行为 |
|---|---|---|
| 正常 | 总实例 < 总上限的 70% | 所有实例按设计运行 |
| 紧张 | 70%–100% | 不再创建**新**的 P4 纯表现实例；已存在的 P4 提前结束，直到回到正常；判定与结算行为不变 |
| 超限 | 达到总上限 | 见 15.4 的丢弃顺序；每次丢弃/拒绝写一条 `debug_record`（kind=`budget_drop`，非技能事件，见 15.5） |

要点：紧张状态下，对玩家**可见的判定行为**与正常状态完全一致；变化的只是画面的装饰程度。

## 15.4 超限丢弃顺序

超限时（或新建实例会使总量超上限时），按以下顺序处理〔D-38 推荐默认〕：

1. 先拒绝创建新的 P4。
2. 再清除已存在的 P4（按 `seq` 小者先，即最老的先丢）。
3. 若仍超限，拒绝创建新的 P3（派生体），再丢弃已存在的 P3：同类内按 `seq` 小者先（最老的先丢）。
4. **不挤掉根判定实例**〔R8 裁决〕：`generation=0` 的判定实例（P0–P2）不会为了给别的实例腾位置而被丢弃；若仍超限，只能拒绝创建**新的**根判定实例，按 P2 → P1 → P0 的顺序拒绝（P0 最后）。
5. 凡拒绝创建根判定实例，必写 `debug_record`（kind=`budget_drop`，detail=`refused_root`）；这属于设计配置错误的信号，应在验收中暴露。

被丢弃的判定实例（仅 P3）的终止方式：

| 方案 | 规则 | 副作用 |
|---|---|---|
| A　按清场处理（推荐） | 视为 `purge`：**不发 vanish、不派生、不补 hit** | 无连锁；但可能少触发 vanish 派生，需文档承认 |
| B　按 `interrupted` | 发 vanish(`interrupted`) | 默认不允许 vanish 派生（契约原因码表），也安全；但会让被动触发层看到“被打断”，语义不准确 |

**推荐 A**〔D-39 推荐默认〕。理由：丢弃是系统自保，不是游戏内事件；不应制造新的 vanish 或派生，否则丢弃自身会引发更多实例创建（压力放大）。丢弃的判定实例数量必须记入 `debug_record`，供验收统计“预算压力下丢弃了多少判定实例”。

## 15.5 debug_record（非事件、非结算记录）

预算丢弃/拒绝创建写入一份**只读 `debug_record`**〔D-39 推荐默认；R9 裁决〕。它不是技能事件，也不是结算记录（契约：事件只有 hit/vanish；结算记录只有四种）；可观察，仅供测试与调试，**任何层不得订阅它来触发逻辑**（含被动触发层、遗物、表现层的逻辑分支）。

| 字段（示例） | 含义 |
|---|---|
| `tick` | 发生 tick |
| `kind` | 本章只用 `budget_drop`（全书统一取值：`budget_drop`、`proc_blocked`、`gen_limit`，后两者属第20章） |
| `detail` | 区分子情形：`refused_create` / `dropped_existing` / `refused_root` / `budget_total` / `budget_caster` / `budget_class` |
| `class` | 预算类别 P0–P4 |
| `skill_id`、`instance_id` | 被拒绝/丢弃者 |

原先的 `budget_total` 并入 `budget_drop`，以 `detail` 区分。

## 15.6 碰撞分桶（只写口径）

大量实例两两检测会爆炸。本书规定**口径**，不规定算法：

1. 接触检测前，把目标与可命中实例按空间位置分入固定大小的格子（桶）；一个实例只与其覆盖到的桶内目标比对〔D-38 推荐默认〕。
2. 候选接触对数应当随局部密度而非全局总量增长；这是验收时的可观察指标（每 tick 候选对数）。
3. 桶尺寸与最大实例判定半径关联：实例覆盖的桶数应有上限（示例：一个实例至多覆盖 9 个桶），超出者须在设计卡中声明为“大范围实例”，并计入更高的预算成本。
4. 分桶**不得改变**结算顺序：同 tick 的接触仍按 14.3 的 `seq`、`target_id` 排序后结算。排序以桶遍历顺序为准是**错误**的。
5. 分桶是内部优化；任何依赖分桶方式的设计（例如“同桶内先到先得”）都不允许写入设计卡。
6. 引擎的物理重叠列表有一步滞后（E5，见 14.9）；本书以 tick 内自己收集接触为准，不依赖其即时性。

## 15.7 伤害数字合并显示

大量 hit 同 tick 命中同一目标会让数字刷屏。合并只作用于**显示**〔D-38 推荐默认〕：

| 规则 | 说明 |
|---|---|
| 结算不变 | 合并不改变任何 hit、伤害份、`final_amount`、`killed` |
| 合并窗口 | 同一目标、同一类型、窗口内（示例：3 tick）的数字合并为一个，显示合计 |
| 暴击/闪避 | 暴击数字、闪避字样不与普通数字合并（暴击口径见第26章候选） |
| 分份显示 | 一条 hit 内多份是否分开显示、合计显示，属第26章候选；合并窗口规则对两者都适用 |
| 数字实例也是 P4 | 伤害数字属纯表现实例，紧张状态下可被丢弃或合并更激进，但**总伤害合计显示必须保留**（至少显示合计） |
| 目标死亡 | 目标死亡后，其未显示的合并数字仍显示最后合计一次 |
| 读取来源（2026-10-18 第二轮，D-94 推荐默认） | 数字合并所用数据只来自 `hit` 事件与 `hit_settled`（含份级 `parts[]`，见 6.4）；**不得读取 `debug_record`**（6.7）。P4 数字被丢弃时，合计显示由结算记录求和得到，不依赖表现实例存活 |

## 15.8 可测试的规则清单

示例数值：总上限 1200，P4 在 70% 起限制。

| 编号 | 前置 | 操作 | 期望的可观察行为 |
|---|---|---|---|
| T-15-1 | 总实例 840（70%） | 再创建 100 个粒子（P4） | 创建被拒绝，`debug_record` 100 条（kind=`budget_drop`，detail=`refused_create`）；判定实例数不变 |
| T-15-2 | 总实例 1200，其中 P4 共 300 | 再创建 50 个 P2 | 先清除最老的 50 个 P4，P2 创建成功；P2 未被丢弃 |
| T-15-3 | 总实例 1200，P4 已为 0，P3 与 P2 满 | 再创建 10 个 P3 | 被拒绝创建；P0/P1 数量不变 |
| T-15-4 | 总实例 1200 全为 P0/P1 | 再创建 1 个 P0 | 被拒绝；`debug_record` detail=`refused_root` 标出配置错误；已存在 P0/P1 不被丢 |
| T-15-5 | 丢弃一个带 vanish 派生的 P3 | 观察 | 无 vanish、无派生；`debug_record` detail=`dropped_existing`（purge 语义，D-01） |
| T-15-6 | 同 tick 40 条 hit 打中同目标、同类型 | 观察显示 | 显示数字数 < 40（合并），合计等于结算总和；结算总和不变 |
| T-15-7 | 同种子同输入、预算紧张 vs 正常 | 比较 hit 序列 | 判定类 hit 的 tick、顺序、数值相同，仅 P4 数量不同 |
| T-15-8 | 分桶开启 vs 关闭 | 比较 hit 序列 | 结算顺序与结果完全相同 |

T-15-7、T-15-8 是核心：**预算与分桶不得改变结算结果**，只能改变装饰与性能。

## 常见误写→正确写法

| 常见误写 | 正确写法 |
|---|---|
| "超限了就随机删几个实例" | 按优先级：先 P4，再 P3/P2；同类内最老的先丢 |
| "为了省预算先丢判定，保留拖尾" | 判定实例最后丢，纯表现先丢 |
| "丢弃实例时也触发它的 vanish 派生" | 丢弃按 purge，不发 vanish、不派生 |
| "被动遗物在实例被丢弃时触发" | `debug_record` 不是触发源，任何层不得订阅 |
| "合并伤害数字就把多条 hit 合成一条" | 合并只在显示；hit 与结算不变 |
| "分桶后同桶内先到先得" | 排序仍按 `seq`、`target_id`；不依赖桶遍历顺序 |
| "预算紧张时火区跳伤变少" | 紧张只影响 P4；判定行为不变 |

# 第20章　组合安全：派生代数、来源链、作用域与实例预算

> 一句话结论：**默认派生只有 1 代，每次施放有总实例预算，每个实例带来源链标记，修饰器默认只管自己的技能**；任何 N 个水晶×M 个遗物的乘积，最终都被预算截住。（本书重点）

## 20.1 为什么要从严〔D-04 已确认〕

D-04 已确认高自由度拼装。N 个水晶 × M 个遗物若各自带分裂、连锁、被动触发，实例数会指数级增长；因此组合安全不靠"作者小心"，而靠三件硬机制：**默认代数上限、来源链标记、总预算**。

## 20.2 派生代数上限

| 规则 | 内容 |
|---|---|
| 代数定义 | 根实例第 0 代；其派生体第 1 代，依此类推 |
| 默认上限 | **1 代**：根实例可派生，派生体默认不再派生〔D-48 推荐默认〕 |
| 加深 | 技能设计卡显式声明 `max_generation = n` 才可更深；修饰器**不能**自行加深 |
| 超限处理 | 超过上限的派生请求直接丢弃，并记一条 `debug_record`（`kind=gen_limit`；`debug_record` 非事件、非结算记录，任何层不得订阅它来触发逻辑）〔D-48 推荐默认〕 |
| 绝对封顶 | 全局硬上限（示例：4 代），设计卡声明不得超过 |

> 状态型派生体的挂载（2026-10-18 第二轮，U-4/D-98 推荐默认）：D-71 的“创建 tick 不判定”只禁止**接触判定**，不阻止状态型派生体（载体 `attached`〔2026-10-18 终审修正〕，给目标挂状态）在创建 tick 完成挂载；挂载失败（目标已失效等）留下的空实例不需要特殊清理，由其 `lifetime` 自然回收。D-71 原文不变。
## 20.3 每次施放实例总预算

1. 每个 `origin_cast_id` 有一个**实例总预算** `cast_budget`（示例：根与所有派生合计 ≤ 64）。〔D-49 推荐默认〕
2. 预算在**创建**实例时扣减；扣完后，后续派生与被动触发的生成请求被截断。截断时优先保留根与较低代数（丢弃原则见第15章）。
3. 截断不是错误：被丢弃的生成请求按 `purge` 处理（不发 hit/vanish、不派生），并记 `debug_record`（`kind=budget_drop`，`detail` 区分单次施放预算或全局预算）。预算截断**不得挤掉根判定实例**。〔D-49 推荐默认〕
4. 全局实例预算（第15章，D-03）与 `cast_budget` 同时生效，取更严者。

## 20.4 来源链标记 `origin`

| 字段 | 含义 |
|---|---|
| `origin_skill` | 最初的技能 id |
| `origin_cast_id` | 最初那次施放的 id |
| `chain_depth` | 因果链环节数（根=0；每次**派生 +1**，每次**被动触发生成效果体也 +1**）。与 `generation` 的关系：`generation` 只数派生，故恒有 `chain_depth ≥ generation`；上限字段统一为 `max_chain_depth`〔D-50 推荐默认〕 |
| `proc_mask` | 本链上已触发过的"触发点"集合（技能派生点或遗物触发点的标识） |

规则：

1. 派生体与被动触发生成的效果体，必须复制并推进父的 `origin`；不得自行创建新的 `origin_cast_id`（否则预算失效）。〔D-50 推荐默认〕
2. **同一来源不重复触发自己**：某触发点的标识已在本链 `proc_mask` 中，则不再触发。〔D-50 推荐默认〕
3. `proc_mask` 只在链内传递；不同 `origin_cast_id` 的链互相独立。
4. 灵感，待核验：RoR2 有名为 procChainMask 的机制，目的与此类似；其具体实现本书未核验，只作灵感，不据此推断细节。

## 20.5 修饰器作用域与继承

1. 修饰器默认 `scope = own_skill`，只作用于所挂技能自身的实例。〔D-51 推荐默认〕
2. 派生体**只继承标 `inheritable = true` 的修饰器**；未标的不影响派生体。
3. `scope = tagged` 需要技能设计卡声明对应标签，否则不生效。
4. 外部做法参考：E2 指出载荷与外部修饰隔离（冷却/充能类例外）。本书借其"默认隔离、显式继承"的精神，不照搬例外清单。

## 20.6 追踪与目标丢失

追踪是**效果体的运动方式**，不是派生，也不是第三个事件。

| 候选 | 规则 | 体验 | 优点 | 代价 | 典型案例 | 与已确认规则兼容性 |
|---|---|---|---|---|---|---|
| A 沿原方向继续 | 目标丢失（死亡/离场）后保持最后朝向直线飞行，直到 `range_end` 或寿命结束 | 自然，不卡顿 | 实例不悬空，无需重新索敌 | 可能飞向空处 | 追踪弹 | 兼容 D-01 |
| B 重新索敌一次 | 目标丢失时重新索敌一次，找不到则按 A | 命中率高 | 更"智能" | 索敌有代价；与分裂叠加可能偏置 | 追踪导弹 | 兼容 |
| C 声明终止 | 目标丢失即终止，原因码 `range_end`（派生默认否，技能显式声明才可）；不使用 `interrupted` | 规则最短 | 简洁 | 浪费玩家投入 | 锁定类 | 兼容；原因码见契约原因码表 |

推荐：**A 为默认**（沿原方向继续，到 `range_end`/`expired` 自然终止）；设计卡可用字段 `on_target_lost: continue | terminate` 声明，`terminate` 以 `range_end` 终止；B 作为需显式声明的扩展。任何情况下目标丢失都不使用 `interrupted`。〔D-52 推荐默认〕

## 20.7 分裂、穿透、弹射、连锁的组合规则

参考 E1（PoE wiki「Projectile」）：碰撞时按 Split > Pierce > Fork > Chain > Return 顺序尝试，每次碰撞只发生一种；Split 只能一次，分裂体视为同一投射物（不会重复命中同一目标）；同时生成的多个投射物对同一目标只有一个能碰撞（防霰弹）。

| 候选 | 规则 | 体验 | 优点 | 代价 | 典型案例 | 与已确认规则兼容性 |
|---|---|---|---|---|---|---|
| A 采用 E1 式优先级与"只一次" | 一次碰撞（同一候选接触）只执行一种碰撞行为（Split>Pierce>Fork>Chain>Return）；Split 与 Pierce 互斥；**分裂时母体以 `hit_end` 终止**，不继续穿透、不再计 `max_hits`；分裂体不可再分裂；分裂体与母体同属一个家族，不二次命中同一目标 | 行为可预期，不炸屏 | 与代数上限天然配合 | 一次碰撞不能既分裂又穿透 | 本书推荐 | 兼容 D-01、D-04；配合 `hit_policy` |
| B 自由组合 | 一次碰撞可顺序执行多个行为 | 爽感强 | 构筑自由度高 | 最坏情况呈乘积 | 极端 build | 与 D-04 从严冲突，不推荐 |
| C 技能自声明 | 设计卡逐技能写碰撞行为优先级 | 灵活 | 精确 | 书写量大，易不一致 | 特殊技能 | 不得突破"一次碰撞一种"；仅可调整优先级顺序 |

推荐：**A（收敛为唯一推荐）**。优先级为 E1 参考做法（推荐默认，不是外部规则）。家族登记按"已发生的候选接触"登记（见第14章），登记后同家族不二次命中同一目标；它与"防霰弹"（同一次出手同时生成的独立实例之间）是两种不同机制，不得混称。〔D-53 推荐默认〕

## 20.8 最坏情况演算（以下全为示例数值）

设定（示例）：`max_generation = 1`（默认）；每次碰撞分裂最多 3 枚；`cast_budget = 64`。

1. **无任何限制的理论值**：N 个水晶各使"齐发数 ×2"，M 个遗物各使"分裂数 ×2"。示例 N=3、M=2：根实例 2³ = 8 个；每根分裂 3×2² = 12 个。总数 = 8 × (1 + 12) = 104。
2. **默认代数上限 1 代**：派生体不再派生，104 就是上界。若允许 2 代，则 8 × (1 + 12 + 12×12) = 1256，直接爆炸。
3. **`cast_budget = 64` 截断**：104 > 64，按创建顺序扣减，后 40 个被丢弃；先保留根（第 0 代）与较早创建者，派生体先被截。
4. **被动触发叠加**：若再有遗物"每次命中触发一枚新弹"，其生成物复制同一 `origin_cast_id`，同样扣这 64 的预算，并受 `proc_mask` 约束不重复触发自己，因此单链总量仍不超过 64。
5. **多次施放**：每次施放各有 64，但全局实例预算（第15章）统一兜底。

| 防线 | 截住什么 | 示例数值 |
|---|---|---|
| 派生代数上限 | 指数增长的层数 | 默认 1 代 |
| `cast_budget` | 单次施放总量 | 示例 64 |
| `proc_mask` | 同源重复触发 | 同一触发点一条链最多 1 次 |
| 全局实例预算（第15章） | 多次施放叠加 | 见第15章 |

## 20.9 防循环小结

循环来源只有三类：派生互相触发、被动触发触发被动触发、修饰器回写自身。对应防线：代数上限、`proc_mask` 加深度、修饰器不得修改 `origin`（18.6）。第21章再叠加"每触发内置冷却"。

## 20.10 常见误写→正确写法

| 常见误写 | 正确写法 |
|---|---|
| 派生体可无限继续派生 | 默认 1 代；加深须设计卡声明 `max_generation` |
| 被动触发生成物自己新建 `origin_cast_id` | 复制并推进父 `origin`，共享 `cast_budget` |
| "修饰器自动作用于所有派生体" | 仅 `inheritable` 修饰器继承 |
| "追踪弹目标死了就用 `interrupted` 终止" | 默认沿原方向继续；`on_target_lost: terminate` 用 `range_end` |
| "分裂体命中同一目标 N 次" | 分裂体与母体同家族，不二次命中同一目标；母体以 `hit_end` 终止 |
| "超预算就报错" | 超预算按 `purge` 丢弃，记 `debug_record`（`budget_drop`） |

# 第21章　被动触发层

> 一句话结论：**遗物只能"读结算记录"，再"生成效果体"或"挂修饰器"，不能直接造成伤害**；循环由来源链标记、深度上限、每触发内置冷却三层共同挡住。〔D-02 已确认范围〕

## 21.1 范围〔D-02 已确认〕

被动触发层属于 D-02 已确认范围：它是遗物玩家侧触发的独立层，不替代施法者闭环，也不是第三个事件。

## 21.2 可读什么：结算记录

| 结算记录 | 载荷 | 典型用途 |
|---|---|---|
| `hit_settled` | `source_instance`, `target_id`, `total`, `killed`, `parts[]{part_index,type}`（2026-10-18 第二轮：补份级 `type`，供 `condition` 按份过滤，U-3/D-94） | "造成伤害时""击杀时" |
| `evaded_all` | `source_instance`, `target_id` | "被攻击全部闪避时" |
| `damage_taken` | `target_id`, `total`, `origin` | "受伤时" |
| `cast_started` | `caster_id`, `skill_id`, `cast_id` | "施放技能时" |

- 结算记录**只读**，且**不是事件**；遗物不得订阅 `hit` / `vanish` 去改结算。〔D-54 推荐默认〕
- 触发在结算记录写出之后的处理段执行（同帧顺序见第14章），不得在结算中途改动结算。
- 表现层读取（2026-10-18 第二轮，D-94 推荐默认）：正式 UI 与表现层同样只读 `hit` 事件与 `hit_settled`（需份级信息读 `parts[]`，不新增事件）；`debug_record` 仅调试面板与性能分析工具可读，任何游戏逻辑层与正式 UI 不得读取（6.7）。

## 21.3 能产出什么

| 允许的产出 | 说明 |
|---|---|
| 生成效果体 | 经技能管线正常创建（如"击杀时在其位置生成一个火区"），伤害走正常 hit / 伤害份流程 |
| 挂修饰器 | 给指定技能/施法者挂临时修饰器（如"闪避后一段时间内冷却缩短"），遵守第16–17章权限与暴露声明 |

**禁止**：直接扣血、直接加伤害数值、直接修改已结算的 hit。理由：直接伤害绕过伤害份、闪避、减免，且无法被预算与来源链约束。〔D-54 推荐默认〕

## 21.4 触发规则字段

| 字段 | 含义 |
|---|---|
| `trigger_id` | 触发实体标识（某遗物的某条触发规则；技能派生点同样用 id 登记），进入 `proc_mask`〔D-55 推荐默认〕 |
| `allow_self_chain`（可选） | 是否允许本触发在同一链上再次触发自己；默认 `false`；设 true 时仍受深度上限与内置冷却约束〔D-55 推荐默认〕 |
| `on` | 订阅的结算记录名 |
| `condition` | 对记录载荷的过滤条件（含按份 `type` 过滤） |
| `chance` | 触发概率，使用可注入种子 RNG（D-09 已确认） |
| `internal_cooldown_ticks` | 每触发内置冷却（tick） |
| `max_chain_depth` | 允许的最大 `chain_depth`（示例默认 1） |
| `produces` | 生成的效果体模板，或挂载的修饰器 |
| `strength_coeff`（可选） | 触发强度系数，见 21.6 |

## 21.5 循环保护：三层叠加

| 层 | 机制 | 挡住什么 |
|---|---|---|
| 1 来源链标记 | 产出继承父 `origin`，并把自己的 `trigger_id` 写入 `proc_mask`；同一 `trigger_id` 在同链上不再触发 | A 触发 B、B 又触发 A |
| 2 深度上限 | `chain_depth` 超过 `max_chain_depth` 则不触发 | 长链 |
| 3 内置冷却 | 同一 `trigger_id` 在 `internal_cooldown_ticks` 内最多触发一次（按持有者计） | 同一帧大量命中同时触发 |

- 三层**同时生效**，任一层命中即不触发。〔D-55 推荐默认〕
- 默认 `internal_cooldown_ticks` 不得为 0；确需"每次都触发"，须显式声明并写明最坏情况，同时有 `cast_budget` 兜底。〔D-55 推荐默认〕
- 触发产出扣的是同一 `origin_cast_id` 的 `cast_budget`（20.3）。若触发本身不由某次施放引发（如怪物攻击引起 `damage_taken`），由触发层为该链开一个独立短链预算（示例上限 8）。〔D-56 推荐默认〕

## 21.6 强度缩放：外部参考

E3（RoR2 Proc Coefficient）：系数是缩放因子，同时乘到触发概率和持续时间；不影响暴击；技能系数不可被修饰。

| 候选 | 规则 | 体验 | 优点 | 代价 | 典型案例 | 与已确认规则兼容性 |
|---|---|---|---|---|---|---|
| A 不引入系数 | 每次触发等权 | 简单 | 零学习成本 | 高频小伤害技能触发过多 | 初版 | 兼容 |
| B 触发强度系数 | 技能/效果体声明 `strength_coeff`，缩放触发概率（及生成物时长）；作者固定，不暴露、不可被修饰 | 连发、环绕不会过度触发 | 控制高频来源；与 D-04 从严一致 | 多一个概念 | 连发、环绕、持续区域 | 兼容；见 17.4 |
| C 只靠内置冷却 | 不引入系数 | 最简 | 实现最短 | 冷却内的多次命中感受粗糙 | 简单遗物 | 兼容 |

推荐：**B**，并保留内置冷却兜底。〔D-57 推荐默认〕

## 21.7 与施法者闭环、D-06 的关系

1. 被动触发生成的效果体不经过施法者闭环（无前摇/冷却），但仍受 `cast_budget` 与代数上限约束。
2. 位移状态期间不能施放其他技能〔D-06 已确认〕；被动触发生成效果体不属于"施放"，可以发生，但不得借此启动新的位移状态。〔D-57 推荐默认〕
3. 被动触发不得再产生 `cast_started`（不允许"触发施放技能"），避免与闭环冲突并形成递归。〔D-57 推荐默认〕

## 21.8 常见误写→正确写法

| 常见误写 | 正确写法 |
|---|---|
| "击杀时对周围敌人造成 50 点伤害" | "击杀时在其位置生成范围效果体"，伤害走 hit |
| 遗物订阅 `hit` 事件 | 只读 `hit_settled` 结算记录 |
| 只靠 `proc_mask` 防循环 | 三层叠加：来源链、深度、内置冷却 |
| `internal_cooldown_ticks = 0` 且无预算说明 | 默认非 0；设 0 须声明，并有 `cast_budget` 兜底 |
| 被动触发递归"触发施放" | 只生成效果体或挂修饰器，不产生 `cast_started` |
| 触发生成物新建 `origin_cast_id` | 继承并推进父 `origin` |

# 项目架构改进与 AI 开发指导书

版本：v1.0（待用户确认执行范围）  
日期：2026-10-12  
适用项目：《弹幕射击 Roguelike × 背包肉鸽 × 轻度搜打撤》

> 本文是后续评审和改进的导航，不是已经完成的重构报告。创建本文不意味着开始改代码、安装工具或发布版本。

## 1. 给项目负责人的简明结论

我们不急着换游戏引擎，也不推倒重写。优先让项目变得更容易理解、更容易安全修改，再根据实测优化性能。

可以把项目理解为一本书：
- 目录：系统和功能地图。
- 章节：每个系统负责什么、如何运行、如何修改。
- 书中规则：玩法与技术约束。
- 使用说明：AI 如何阅读、开发、测试和交付。
- 修订记录：为什么改变，旧方案为什么不再使用。

这本书应是一组有清晰目录的文档，而不是一份无限变长的大文件。目录帮助 AI 按需阅读，避免每次重新阅读全部代码。

三个核心目标：
1. 数据驱动：增加同类型内容时，尽量修改配置，而不是重复编写逻辑。
2. 高扩展性：一个系统的变化，尽量不要求修改许多无关系统。
3. 性能可控：通过测量确认瓶颈，优化后证明收益，而不是凭感觉。

## 2. 当前判断的证据与限制

已经只读抽查了项目规范、技能编译与运行链路、主循环、空间哈希，以及武器重算和水晶入装逻辑。

值得保留的基础：CFG 集中配置、技能编译边界、只读构建、稳定排序、施放快照、空间哈希、对象池、性能护栏和测试门禁。

候选改进点：
- 全局状态和跨文件直接引用增加理解与修改成本。
- 追加扩展与包装逻辑可能使执行路径分散。
- 部分技能碰撞路径遍历全部怪物，需测量效果数量与怪物数量增长时的成本。
- recomputeWeapon 在 playing 帧中执行，可评估版本缓存或脏标记；这不等于技能编译器每帧执行。
- 临时数组、碰撞记录和排序可评估分配与 GC 成本。

限制：尚未完成全项目审查、当前门禁核验和性能基线。以上候选点不能直接当作已证实的根因，也不能据此承诺帧率提升幅度。

## 3. 为什么每次开发可能很慢

不要简单判断为“AI 不会写代码”或“引用太多”。一次工作包含多个阶段：

| 阶段 | 慢的可能原因 | 应记录什么 |
|---|---|---|
| 理解需求 | 反馈现象与预期不清晰 | 用户操作、实际结果、期望结果 |
| 恢复上下文 | 规则分散、版本冲突 | 阅读哪些文档、多久找到真源 |
| 定位问题 | 隐式依赖、全局状态、包装入口 | 实际读取的文件和调用链 |
| 实现修改 | 一处变更影响多个系统 | 修改文件数、接口变化 |
| 验证 | 回归链路多、环境不稳定 | 局部与全量测试耗时 |
| 交付 | 文档、版本、提交和独立部署 | 各步骤耗时与失败原因 |

先对几轮真实任务记录耗时，再决定优先改什么。保留必要验证，不以跳过测试来制造“开发变快”。

用户反馈推荐格式：
- 我在哪里操作？
- 我做了什么？
- 现在发生了什么？
- 我希望发生什么？
- 能否重复发生？是否有截图、录像或版本信息？

不要求用户使用编程术语。AI 负责把反馈转成技术问题；信息不足且影响判断时再提问。

## 4. 模块化：采用原则

模块化不是按文件行数拆分。它是让每个系统有明确职责、接口和状态所有权。

例如技能系统：配置负责内容定义；编译器负责组合规则；运行时负责执行效果；存档负责保存与迁移；UI 获取结果而不重复实现规则。

开发速度与运行性能分开看：
- 清晰边界通常帮助定位、协作和减少误改。
- ES modules 提供显式 import/export 和独立作用域，但不直接提高帧率。
- 碰撞算法、对象分配与渲染成本需要单独优化。
- 文件拆得过碎也会增加跳转成本。

推荐路线：先补模块契约和依赖地图，再选择低耦合部分试点 ES modules。浏览器原生模块不要求引入 React、npm 或打包器。迁移前检查全局变量、脚本顺序、启动副作用、循环依赖、测试加载方式和静态托管路径。

暂不默认采用全面 ECS、TypedArray 化、大型 UI 框架、微服务或更换游戏引擎。只有明确需求与测量结果证明必要时再讨论。

## 5. “项目之书”的内容组织

先沿用现有文档，不建立第二套互相矛盾的规则源。

建议目录：
1. 阅读入口：项目目标、文档权威和常用定位。
2. 架构地图：系统职责、依赖、启动顺序和关键执行链。
3. 玩法规则：继续引用现有权威玩法文档。
4. 系统章节：技能、背包、秘宝、属性、存档、UI、渲染和输入。
5. 操作指南：新增内容、修改机制、定位故障。
6. 性能章节：预算、场景、测量方法与结果。
7. 验证与交付：测试、版本、部署和回退。
8. 决策记录：每次重要架构取舍的原因。
9. 反馈与提案入口：区分待确认问题、已确认需求和已完成变更。

每个系统章节固定包含：
- 负责什么、不负责什么。
- 入口文件、关键符号、搜索关键词。
- 公共接口与输入输出。
- 谁可以写入哪些状态。
- 依赖、不可破坏的约束。
- 常见变更及验证范围。
- 性能预算或已测量热点。
- 关联规则、决策和待解决问题。

优先用文件名、符号和关键词定位，行号只作辅助。AI 不应依靠长期不更新的行号理解项目。

## 6. 文档权威与更新流程

本文不覆盖 AGENTS.md 和既有开发铁律。

技能规则继续遵循现有权威链：用户明确铁律 > skill_system_development_contract_v1.0.md > design_crystal_skill_system_v0.5.md > 旧设计与注释；接口与数据形状查询 skill_system_interface_v1.md。代码用于核验实际行为；代码与规则冲突时登记差异并确认，不能静默把实现当成新的玩法规则。

每条反馈按以下流程处理：
反馈 → 澄清 → 归属系统 → 影响评估 → 提案 → 必要确认 → 修改与验证 → 更新权威章节 → 记录交付。

状态建议：待澄清、待确认、已批准、实现中、待验收、已完成、已否决。

AI 可以替换过时说明，但应保留必要历史：旧表述标注“已被取代”，链接到新规则与决策。未批准的想法不能写成已经生效的玩法。

自动化可以提取文件清单、脚本顺序、配置字段、测试列表并检查链接；不能保证玩法解释和架构理由正确。代码与文档需要同轮评审和版本管理。

## 7. 分阶段执行与验收

### 阶段一：建立事实基线

只读审查系统边界、调用链、状态写入和测试范围；运行当前门禁，建立代表性玩法与压力场景的性能基线。

产物：架构地图、风险清单、耗时记录、测试与性能基线。
验收：每项结论标注为代码事实、测量结果或待验证推断；没有混淆三者。

### 阶段二：建立项目之书

整理现有权威文档的导航，优先补高频修改系统的模块契约、操作指南和决策记录，不重复抄写全部规则。

验收：一个新 AI 能从短入口定位指定系统、规则、入口和验收方法；不存在新增冲突真源。

### 阶段三：小范围结构试点

选择一个低耦合、测试充分的边界，收紧接口与状态写入责任；如收益明确，再试点 ES modules。遵循现有追加独立区块、单行接入等约束；需要改变约束时先提交决策并确认。

验收：玩法不变、门禁通过、关键链路通过；比较修改范围与理解成本，并记录迁移成本。

### 阶段四：优化实测热点

针对测量证明的热点，评估空间查询、缓存、复用缓冲和局部数据布局。优化不能破坏稳定排序、命中规则、事件预算或施放快照。

验收：同环境、同场景、同质量档对比 CPU 帧耗、长帧、对象数量等指标；记录收益与副作用。结构改善与性能改善分别报告。

### 阶段五：逐步推广与交付

试点成功后才扩大范围。每轮改动控制规模，单独提交，可回退；不得同时大改玩法、存档与执行链。

交付：按现有规范完成全量门禁、代表性浏览器及手机验收、文档和版本同步、commit、push，并重新发布独立托管站。GitHub push 不等于正式站已更新。

文档所列历史测试数只作参考，当前数量与结果以本轮真实门禁输出为准。不得将未运行测试写成已通过。

## 8. 环境与工具策略

当前保留纯静态 HTML、全局 JavaScript 和 Canvas 2D 技术路线。本文使用 Markdown，游戏运行时不新增依赖。

优先复用已安装的 Git、Node、bash、Python 与现有浏览器验证工具；使用前检查可用性，不假定本机环境完整。自动化浏览器不等于真实手机验收。

可选文档工具：内容结构稳定后评估 Material for MkDocs；只用于生成文档站，不并入游戏运行时。当前不安装、不作为开发前提。

当前不采用 Backstage：它适合较大规模的软件目录与开发者平台，本项目先借鉴目录和所有权思想即可。

AI 可自行决定：只读定位方式、分析方法、文档组织建议、已授权任务内的小步实现细节、已有工具的非破坏性使用。

必须确认：玩法关键选项、大规模重构范围、存档破坏性变化、全局或系统级安装、收费服务、凭证与第三方授权、删除或覆盖重要资料、发布和回滚目标。用户批准本文件不等于授权这些操作。

系统安装前说明用途、替代方案和影响。凭证不要求用户直接贴到聊天中，不写入源码或公开文档。

## 9. 后续 AI 的工作约定

1. 开始前读取 AGENTS.md，修改前读取开发规范；技能任务再读技能总纲与对应接口真源。
2. 先说明目标、范围和验收，不上来整读大型代码文件。
3. 定位采用搜索符号后局部阅读，记录必要调用链。
4. 先说明根因和证据，再给方案；不把猜测表述为事实。
5. 可调数值归 CFG，遵守加载顺序、CSS 同步和版本要求。
6. 并行任务划分独占文件；共享文件串行集成。
7. 实现后核对代码、玩法文档、接口说明和测试是否一致。
8. 如不能完成测试、真机验收或部署，明确标注未完成项，不宣称完整交付。
9. 对项目负责人使用易懂语言，技术决策说明收益、风险与成本。
10. 不以更换工具代替理解问题，不以跳过验证代替提高速度。

## 10. 成熟思想与参考来源

以下为本轮调研参考，不是必须安装的插件或项目依赖。

- Parnas：信息隐藏与模块划分。围绕可能变化的设计决策划分模块，而不是机械切分处理步骤。原论文条目：https://dl.acm.org/doi/10.1145/361598.361623 （本轮未抓取全文，不作逐字引文。）
- MDN：浏览器原生 JavaScript modules。https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules
- arc42：可裁剪架构文档骨架。https://arc42.org/overview
- C4 model：分层架构地图。单个 JS 文件不自动等于 C4 的容器。https://c4model.com/
- ADR：重要决策的背景、取舍和后果记录。https://adr.github.io/
- Diátaxis：区分教程、操作指南、参考和解释。https://diataxis.fr/
- Material for MkDocs：Markdown 文档站候选。https://squidfunk.github.io/mkdocs-material/
- Backstage Catalog：借鉴系统目录与所有权元数据，暂不部署。https://backstage.io/docs/features/software-catalog/
- Strangler Fig：借鉴渐进替换，而非一次推倒重写。https://martinfowler.com/bliki/StranglerFigApplication.html
- Bounded Context：在确有不同领域模型时划边界，不等同于每个文件或微服务。https://martinfowler.com/bliki/BoundedContext.html

## 12. Matt Pocock 技能接入工作流

记录日期：2026-10-12。来源：https://github.com/mattpocock/skills

### 接入状态与边界

本会话技能导入工具已分别返回以下四项创建成功：`diagnosing-bugs`、`codebase-design`、`writing-for-agents`、`tdd`。`grill-with-docs` 已在当前助手可用技能列表中；没有安装整个仓库。

这些是助手按需加载的工作指引，不是游戏运行依赖。此次接入不代表已在本机 Claude Code、Codex 或其他代理中安装，也不保证新会话或其他助手自动拥有它们。后续任务开始时检查技能可用性；可用则激活并读取，不可用则报告并按项目规范完成对应步骤。

### 按任务加载

| 任务触发条件 | 加载技能 | 阶段完成标准 |
|---|---|---|
| 玩法需求模糊、关键选项或术语存在歧义 | `grill-with-docs` | 明确预期行为、规则归属与验收；仅向用户询问会影响决策的问题 |
| 修改模块接口、职责边界或评估架构 | `codebase-design` | 说明依赖、状态所有权、影响范围与方案取舍 |
| 故障、异常或性能回退 | `diagnosing-bugs` | 建立复现与证据，验证根因，修复后以回归测试确认 |
| 新功能或修复适合自动化行为测试 | `tdd` | 小步执行失败测试 → 最小实现 → 回归验证 → 必要整理；测试先失败于目标行为而非环境问题 |
| 创建或修改 AI 阅读的项目文档、入口说明 | `writing-for-agents` | 指针写明读取条件，规则保持单一真源，步骤具有可检查的完成标准 |

每次只加载任务所需技能。简单文案或配置调整按实际验证范围执行；技能不要求每轮机械走完所有流程。

### 与现有开发流程的结合

1. 读取项目入口及对应权威规则，确认技能是否可用。
2. 按上表选择工作方法，形成范围与验收标准。
3. 完成诊断或设计，再在已批准范围内小步实现与验证。
4. 更新受影响的权威章节，记录实际测试结果与未完成项。
5. 代码交付继续执行项目既有门禁、版本同步、提交和独立托管发布要求。

项目约束优先于通用技能建议：CFG、全局脚本加载顺序、末尾独立区块、CSS 三处同步、文件所有权和交付门禁继续有效。需要调整项目约束时先提出决策，不由技能自动覆盖。

用户已同意接入上述技能；该同意不等于授权后续收费、系统级安装、凭证操作、破坏性变更或发布回滚。此章节记录方法与状态，不宣称架构优化或测试已经完成。

最终原则：每一步可解释、可验证、可回退；让项目之书帮助开发，而不是成为额外负担。

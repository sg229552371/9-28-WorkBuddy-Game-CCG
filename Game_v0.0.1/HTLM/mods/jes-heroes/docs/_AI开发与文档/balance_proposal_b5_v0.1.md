## 1. B5-A 局内等级成长曲线

### 1.1 口径与两版公式

设计书 §8.5 表 1 给出的是**通用等级成长公式**「该等级属性初始值 = 属性初始值 × 成长值」（`game_design_proposal.md:878`），而「成长值 `+1`」与「乘算」的具体衔接**未拍板**（§12 #38，`game_design_proposal.md:1206`）。本提案用同一个「属性倍率」标尺把两版并列：

- **加算版（线性）**：`M_add(lv) = 1 + r × (lv − 1)`
- **乘算版（几何）**：`M_mul(lv) = k ^ (lv − 1)`
  - 为使两版在 **Lv100 处同值**、可与已发布的技能等级系数 `g(lv)` 对齐，取 `r = 0.06`（= `CFG.skillScaleBy.levelGrowth`，`js/config.js:1307`）、`k = 6.94^(1/99) ≈ 1.01976`。
  - 说明：§12 #38 原文写「成长系数^**等级**」，按字面 `k^lv` 会使 **Lv1 ≠ 初始值**；本表统一取 `k^(lv−1)`，让 **Lv1 = 1.00× 初始值**，与「初始等级 = 1」的表结构自洽（`game_design_proposal.md:872`）。

> `M(lv)` = 「该等级属性 ÷ Lv1 初始属性」的倍率，对 hp / atk / def 各属性、各英雄通用（前提是成长按初始值比例，见 §1.3 推荐）。

### 1.2 「等级 → 属性倍率」加算版 vs 乘算版（并列对比）

| 等级 | 加算版 `1 + 0.06×(lv−1)` | 乘算版 `1.01976^(lv−1)` | 差值（乘算 − 加算） |
| ---- | ---- | ---- | ---- |
| **Lv1** | **1.00** | **1.00** | 0.00 |
| **Lv5** | **1.24** | **1.08** | −0.16 |
| **Lv10** | **1.54** | **1.19** | −0.35 |
| **Lv20** | **2.14** | **1.45** | −0.69 |
| **Lv30** | **2.74** | **1.76** | −0.98 |
| **Lv50** | **3.94** | **2.61** | −1.33 |
| **Lv75** | **5.44** | **4.25** | −1.19 |
| **Lv100** | **6.94** | **6.94** | 0.00 |

**曲线形态**：两版同在 **Lv1 = 1.00×、Lv100 = 6.94×** 两端点重合；加算版**早早抬升、后段放缓**（前期给得猛）；乘算版**前期极平、后期加速**（Lv50 才到 2.6×，末段陡升）。

一句话依据（每条）：
- Lv1 = 1.00×：所有等级配表都以「初始等级 1」为基准（`game_design_proposal.md:872`）。
- 加算版数值 1.24 / 1.54 / … / 6.94 直接等于既有 `g(lv)` 在对应等级的值（`skill_effect_balance_v0.1.md:27~29`），**与技能等级系数同源、零新增口径**。
- 乘算版数值由 `1.01976^(lv−1)` 算得，`k` 取 `6.94^(1/99)` 是为「Lv100 与加算版/技能系数同为 6.94×」；若改用整数手感 `k = 1.02`，Lv100 ≈ **7.10×**（略高于 6.94，需另行确认收口）。
- 差值列点出两版的手感分歧点：**Lv50 附近差最大（−1.33×）**，即「中期（Lv10~Lv60）体验」是两版唯一真正的分野。

### 1.3 推荐公式（含 `CFG` 字段名建议）

**推荐：加算版（线性），每级按初始值固定比例成长。**

理由（每条一句）：
1. **同源**：`r = 0.06` 直接复用 `CFG.skillScaleBy.levelGrowth`（`js/config.js:1307`），技能/英雄两条曲线口径统一，无需维护第二套数字。
2. **与现有线性惯例一致**：敌人 `monsterLevel` 成长系数 `1 + (lv−1)×0.12`（`js/config.js:78`、`js/game.js:731`）与局外成长（`CFG.outLevel.growth = { hp:8, atk:2, def:1 }`，线性，`js/config.js:2088`）**都是加算**；沿用它可避免「同一游戏两套成长哲学」。
3. **乘算版风险**：若沿用技能同源的 +6%/级几何，Lv99 倍率达 `1.06^98 ≈ 312×`（数值爆炸）；只有把 `k` 压到 `≈1.02` 才可控 —— 而 `1.02^(lv−1)` 线性近似后**与加算版差异微小**（Lv50 仅差 1.33×），**收益不足以承担几何外推的失控风险**。

**`CFG` 字段名建议（新增，供策划填；不改现有逻辑）**：

| 建议字段 | 建议值 | 含义 |
| ---- | ---- | ---- |
| `CFG.runLevel.mode` | `"add"`（备选 `"mul"`） | 成长公式开关：加算 / 乘算 |
| `CFG.runLevel.addGrowth` | `0.06` | 加算版每级成长率（×初始值），复用 `skillScaleBy.levelGrowth` |
| `CFG.runLevel.mulFactor` | `1.01976` | 乘算版每级系数（`mode:"mul"` 时生效） |
| `CFG.runLevel.stats` | `["hp","atk","def"]` | 参与局内等级成长的属性白名单 |
| `CFG.runLevel.maxLv` | `99` | 与 `CFG.levelUp.curve.maxLv`（`js/config.js:1706`）同步 |
| `CFG.runLevel.baseFrom` | `"heroInit"` | 成长基数 = 各英雄该属性初始值（`CFG.heroes[].hp/atk/def`） |

> 落地方式：建议**并入现有 `CFG.levelUp.baseStatGain`**（`js/config.js:1717`），把「固定绝对值」改为「初始值 × 成长率」，避免新增并行通道。**本提案不改代码，仅提供字段名与值。**

### 1.4 自洽核对：现值 vs 推荐曲线（必须摊开说清）

现值为**绝对增量**（§0.1），折算成倍率后**随初始值剧烈漂移**，与 §1.2 的通用倍率表**不自洽**：

| 参考英雄 | 属性 | Lv1 | Lv100（现值，绝对增量） | 现值倍率 | 推荐（6%/级）倍率 | 结论 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| H001 猎手 | hp | 94 | 94 + 14×99 = **1480** | **15.7×** | 6.94× | 现值偏陡 ~2.3 倍 |
| H001 猎手 | atk | 16 | 16 + 3.5×99 = **362.5** | **22.7×** | 6.94× | 现值偏陡 ~3.3 倍 |
| H001 猎手 | def | 2 | 2 + 0.5×99 = **51.5** | **25.8×** | 6.94× | 现值偏陡 ~3.7 倍 |
| H009 守护者 | hp | 155 | 155 + 14×99 = **1541** | **9.9×** | 6.94× | 现值偏陡 |
| H009 守护者 | atk | 8 | 8 + 3.5×99 = **354.5** | **44.3×** | 6.94× | 现值偏陡 ~6.4 倍 |
| H009 守护者 | def | 8 | 8 + 0.5×99 = **57.5** | **7.2×** | 6.94× | 接近 |

- **一句话依据**：现值对**低初始值属性**（如 H009 攻击 8、H001 防御 2）放大到 25×~44×，对**高初始值属性**（如 H009 生命 155）仅 9.9× —— 说明**绝对增量会让「短板属性」被过度补偿**，破坏角色间定位差异（`game_design_proposal.md:630`）。
- **参考锚**：敌人同等级线性成长为 `1 + (lv−1)×0.12 = 12.88×`（Lv100）。英雄若收口到 6.94×，则**同等级英雄成长弱于敌人成长**；若沿用现值 ~15×~26×，则**英雄远强于敌人**。该强弱锚需与「关卡 `hpMul` 曲线」一并拍板（`CFG.levelCurve.rows`，`js/config.js:2298~2323`）。

### 2.2 逐项一句话依据

- **占格 = `[1,1]`（全阶统一）**：`makeChestItem()` 硬编码 `shape:[1,1]`（`js/items.js:227`）；§6.3 规定「叠加后仅占 1 格」（`game_design_proposal.md:463`），故占格与阶数解耦、恒为 1 格。
- **重量 8 / 12 / 18 / 26 / 36**：直读 `CFG.chestQualities[].weight`（`js/config.js:1968~1972`）；阶梯递增、高阶更沉，呼应「越贵越难带」的取舍（§9.4，`game_design_proposal.md:1089`）。
- **堆叠上限 5 / 5 / 5 / 5 / 3**：直读 `CFG.chestQualities[].stackMax`（`js/config.js:1968~1972`）；神话阶用 3 收口，避免顶级货物被轻易批量携带。
- **价值 20 / 60 / 150 / 400 / 1000**：与 §6.6「物品固定价值表」逐行一致（`game_design_proposal.md:532~536`），**折算链自洽**（20→10、60→30、150→75、400→200、1000→500 结晶）。
- **重量阈值联动**：`CFG.weight.threshold = 100`、`minFactor = 0.2`（`js/config.js:2070`）；满叠 **史诗(90) 未超阈值、神圣(130)/神话(108) 已超** —— 高阶货物天然触发超重惩罚，符合 §9.2 线性递减曲线（`game_design_proposal.md:1068~1074`）。
- **命名**：本表所有字段落在真源 **`CFG.chestQualities`**；**唯一缺口 = 占格未进 `CFG`**（见 §3 第 5 条）。

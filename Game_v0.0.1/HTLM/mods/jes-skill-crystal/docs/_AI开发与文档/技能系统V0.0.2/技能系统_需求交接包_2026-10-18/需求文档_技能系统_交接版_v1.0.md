## 第 1 章　项目全景

### 1.1 游戏是什么

一款**弹幕 Roguelike × 背包 Roguelike × 搜索撤离**玩法融合的独立游戏，多平台 16:9 横版。

| 维度 | 设定 |
|---|---|
| 主线 | 99 关，通关后进入赛季模式 |
| 角色 | 共 12 个角色，首发解锁前 6 个 |
| 等级 | 双层体系：局内 LV1 起 + 局外角色等级（局外材料机制待定） |
| 宝箱 | 5 阶（普通/高级/史诗/神圣/神话），初期仅实现前三阶 |
| 属性卡牌 | 4 档品质（白/蓝/紫/金），永久局外资产，仅在工匠地图生效（该地图无敌人） |
| 统一道具系统 | 战争雕像/女神雕像/宝箱/工匠雕像共享同一通用道具系统，仅外观不同；圈内读条 2–3 秒生效 |

### 1.2 技能系统的硬规则（与游戏层约定的接口）

- **所有英雄均为独立个体**，可触发所有判定，但**同一判定圈内多名英雄不能同时触发**
- **武器绑定初始主动技能，无普攻**；水晶影响初始技能与稀有技能

## 第 2 章　技能系统的定位：拆成两份文档

### 2.1 拆分决定（2026-10-18 已确认）

用户最初的出发点是**「一个技能编辑器——主要是表现层的东西，可以自定义技能中的积木」**。现有书稿实际写的是运行时的做菜工序（厨房），不是菜谱编辑器（作者界面）。2026-10-18 定案拆分为：

```
《技能编辑器规格》          《技能 CFG 存档格式 Schema》         《技能运行时契约》
（作者层 · 人填写）    →     （唯一契约 · 机器读写）      →     （引擎层 · 机器执行）
积木清单、暴露参数、            字段定义、取值范围、版本号            结算顺序、事件与记录、
预览与报错                        （现有附录 B YAML 是雏形）          预算与确定性
       目前 0 字，待写                                            现有书稿 v0.2.6 就是它
```

### 2.2 对应关系（积木 = 载体的预设组合）

| 用户口中的"积木" | 运行时底层是什么 |
|---|---|
| 飞弹 | 独立载体 + 有运动 + 有寿命 |
| 爆炸 | 瞬时载体 + 寿命 0 + 同 tick 结算 |
| 光环 | 独立载体 + 原地不动 + 周期跳 |
| 护盾 | 附着载体（attached）+ 挂在目标上 + 有寿命 |

**4 类载体是积木的公共父类，积木是它们的预设组合。** 这是整个系统"数据驱动"的真正含义：程序只写 4 套载体逻辑，编辑器可无限出积木。

### 2.3 两份文档的边界声明

- 《技能运行时契约》：定义「CFG 被读进来之后，世界如何运转」。**不定义**编辑器界面、不定义帧率/实例数验收、不定义美术资源。
- 《技能编辑器规格》：定义「人如何填出一份合法 CFG」。**不定义**运行时算法，但可以引用运行时契约的字段约束做校验。

### 2.4 《技能编辑器规格》的核心

#### 核心定义（一句话）

> **定义"一个技能在数据上是什么"——把策划脑子里的技能，变成一份合法、可预览、可保存、能被运行时 100% 还原的 CFG。**

#### 它为什么存在（唯一理由）

让不会写代码的人，通过**选积木 + 填参数**的方式造出技能，且造出来的东西运行时一定跑得起来、跑出来的结果就是预览里看到的样子。

#### 四根核心柱子

| # | 柱子 | 要定义什么 | 为什么是核心 | 现状 |
|---|---|---|---|---|
| **柱 1** | **积木体系**<br>（灵魂，用户最初出发点） | 积木 = 有名字的能力预设（飞弹/爆炸/光环/护盾/链电/冲刺…）；每块 = 四类载体之一的预设组合 + 默认参数；每块声明「哪些参数给作者填、哪些锁死、哪些可被水晶遗物改」；**积木数量不固定**，新增走登记流程不硬塞 | 没有积木体系，"自定义技能"就退化成"填一大堆参数"，失去可扩展性 | ⚠️ 只有 4 类载体定义，积木清单为 0 |
| **柱 2** | **表单与校验** | 每个积木的字段表：字段名/类型/默认值/取值范围/单位/必填/新手进阶分级；非法组合检测；报错定位到具体字段 | 保证产出的 CFG 合法；校验规则必须从运行时契约反推 | ⚠️ 24.2 八栏是逻辑视角，需转译为表单视角 |
| **柱 3** | **表现层配置**<br>（用户最在意、目前**完全空白**） | 特效/音效/动画/拖尾/镜头/伤害数字/状态图标；逻辑 tick ↔ 动画帧对齐；填完即可预览 | 用户的编辑器"主要是表现层的东西"；没有表现配置，编辑器就不是编辑器 | ❌ **零**（书稿第 1 章明确排除 D-08） |
| **柱 4** | **组织与版本** | 技能 ID 命名规范、角色归属、技能池、标签分类、搜索复制；存档格式与 Schema 版本、旧档迁移 | 让 12 角色 × 每角色多技能 × 水晶池能被管理起来 | ❌ 零（只有一个 `skill_id` 字段名） |

#### 核心交付物

一份《技能编辑器规格》，使得：
- 程序能照它做出编辑器界面
- 策划能照它填出技能
- 填出来的东西能被运行时契约 100% 还原

#### 核心边界（不做什么）

| 不做 | 归谁 |
|---|---|
| 不定义运行时怎么算 | 运行时契约 |
| 不定义帧率/实例数验收指标 | 项目层文件 |
| **不暴露内部工序顺序**（免疫→次数→属性→clamp 是引擎固定工序，编辑器只给「预设包勾选 + 数值填值」） | 引擎写死 |
| 不校验物品合法性、不做输入缓冲、不做 UI 适配 | 见 IF-1…IF-7「我们不做」 |

#### 一条设计红线

**顺序不可配，数值可配。** 一旦允许策划配置结算顺序，组合数爆炸、验收写不完、任何一个配错都是查不出来的平衡灾难。

### 2.5 《技能运行时契约》的核心

#### 核心定义（一句话）

> **定义"一份 CFG 被读进来之后，世界如何运转"——且必须唯一、确定、可复现、可验收。**

#### 它为什么存在（唯一理由）

保证「同一份配置 + 同一条种子 + 同一次操作序列」在任何时候都算出**完全相同**的结果，从而让技能组合的每一个行为都可预测、可验收、可调。

#### 四根核心柱子

| # | 柱子 | 要定义什么 | 为什么是核心 | 现状 |
|---|---|---|---|---|
| **柱 1** | **统一效果体模型**<br>（地基，D-01） | 一切技能产物都是效果体（子弹/区域/护盾/召唤物/状态/纯表现）；四类载体 `none` / `self` / `independent` / `attached`（`self`＝自身载体：位移状态＋跟随判定体，用于冲刺、跳跃、有路径命中的位移；此处原稿写作 `instant` 系摘要笔误，2026-10-18 已按主书稿第 8 章订正）；每条有生命周期、终止原因码、事件、结算记录、派生规则 | 没有这层，每类技能都要写一套逻辑，**积木就不可能无限扩展** | ✅ 已完成（第 5–8 章 + D-106） |
| **柱 2** | **确定性运行时**<br>（D-09） | 固定时间步长 + 可注入随机种子 + FIFO + 同帧顺序 + 容差比较；表现 RNG 与逻辑 RNG 分离；承诺「同平台、同种子逐次一致」 | 没有确定性，编辑器填完的参数无法验证，**73 条验收例子全部失去意义** | ✅ 已完成（第 14 章） |
| **柱 3** | **逐份结算与事件最小化** | 一次接触 = 一条 hit，hit 内含多个「份」（伤害份/治疗份/控制份…）；**事件只有两个**（hit / vanish）、**结算记录只有四种**；份级免疫（D-104）与份级表现数据挂在 `parts[]` | 组合不爆炸；新效果类型只需注册新份类型，不动框架 | ✅ 已完成（第 11 章 + 6.4） |
| **柱 4** | **组合安全与规模控制** | 派生代数上限、来源链、作用域、`chain_depth` 防循环；修饰器三档权限；被动触发防循环三层 + 内置冷却；实例预算五级 P0–P4 + 超限丢弃优先级 | 技能可以自由组合（这是乐趣来源），但**不能互相打死** | ✅ 已完成（第 15、20、21 章） |

#### 核心交付物

一份《技能运行时契约》+ 73 条验收例子 + 机器可读 Schema，使得：
- 程序能照它实现引擎
- AI 能照它验收（同一输入必然同一输出）
- 编辑器能照它做校验与预览

#### 核心边界（不做什么）

| 不做 | 归谁 |
|---|---|
| 不定义编辑器界面 | 编辑器规格 |
| 不定义美术/音效资源 | D-08 明确排除 |
| 不定义帧率/实例数验收指标（只定分级与丢弃行为） | 项目层文件 |
| 不做联网同步 | D-09 明确排除 |

### 2.6 两份核心的对照（防跑偏速查）

| 维度 | 技能编辑器规格 | 技能运行时契约 |
|---|---|---|
| 一句话核心 | 技能在数据上是什么 | CFG 进来后世界怎么转 |
| 服务对象 | 人（策划/玩家） | 机器（引擎/验收 AI） |
| 唯一理由 | 让人不写代码也能造技能 | 让同一输入必然同一输出 |
| 灵魂 | 积木体系 | 统一效果体模型 |
| 最大风险 | 表现层缺失 → 编辑器不成编辑器 | 失去确定性 → 全部验收失效 |
| 最怕的错误 | 把内部工序暴露给用户配 | 让表现反向影响逻辑 |
| 当前完成度 | **0%** | **约 90%**（规则主体，剩 10 个洞） |

- 编辑器**写入**它，运行时**读取**它，是两者之间**唯一不可变契约**

## 第 10 章　术语约定

| 术语 | 含义 | 出处 |
|---|---|---|
| 效果体 | 一切技能产物的统一容器（子弹/区域/护盾/召唤物都是） | D-01、第 5 章 |
| 载体 | 效果体的存在方式，四类：`none`（瞬时无实例）/`self`（自身载体：位移状态＋跟随判定体，冲刺、跳跃、有路径命中的位移）/`independent`（独立运动）/`attached`（附着有寿命）。注：本表原写作 `instant`，系对主书稿第 8 章的摘要笔误，2026-10-18 已订正为 `self` | 第 8 章、D-106、F-43 |
| 积木 | 编辑器侧有名字的预设（飞弹/爆炸/光环/护盾…），= 载体的预设组合；数量可扩展，当前 4 类载体是公共父类 | 第 1 章（v0.2.5 修正口径） |
| 暴露部位 | 单个技能开放给玩家自定义的参数点，默认 4 个（伤害/冷却/范围/数量），可 3 可 6，与积木数无关 | 24.1 |
| 修饰器 | 水晶与遗物的统一抽象，三档权限（生成时/快照后/实时） | 第 16–17 章 |
| 份（part） | 一条 hit 内的独立结算单元（伤害份/治疗份/控制份…），各有独立类型、减免、闪避 | 第 11 章 |
| 被动触发层 | 读结算记录生成效果体或挂修饰器的层，防循环三层 | 第 21 章、D-55/D-89 |
| 施法者闭环 | 索敌→前摇→出手→冷却 | 第 4 章 |
| hit / hit_settled | 仅有的两个事件；结算记录只有四种 | 第 6 章、D-94 |
| 份级免疫 | `immune_flags` 按份注册（immune_control/knockback/debuff…），无敌=预设包 | D-104 |
| 装配公共冷却 | 卸下/替换任一装配槽触发同一 CD，冷却期全槽拒绝操作 | D-105 |
| 技能石/辅助石/技能栏多槽 | = 主动技能 / 武器模块 / 局内武器栏（项目术语约定） | 游戏层 |

## 二、现状瓶颈（调研实证，附行号）

**逻辑层尚有余量，首崩在渲染层。**

| 序 | 瓶颈 | 证据 | 目标量级 |
|---|---|---|---|
| **1** | **渲染 drawImage**：每怪 1 次带缩放 drawImage + save/restore + 血条 2×fillRect，**正常画质零剔除** | `game.js:3579-3661`、`3599-3602`、`3609-3611`；剔除仅低画质 `3578-3580` | 3000×(drawImage+2rect+save/restore) ≈ **12000+ 调用/帧** |
| **2** | **弹幕矢量绘制**：每弹 `beginPath+arc+fill`（无 drawImage）；2000 弹 | `game.js:3663-3679` | 2000 次路径构建/帧 |
| **3** | **状态切换**：精英受击 `ctx.filter="brightness(2)"`（滤镜=整层重绘）；粒子逐颗改 `globalAlpha` | `3600`、`3778` | 滤镜是最贵项 |
| **4** | **空间哈希去重 O(k²)**：`query` 用 `indexOf` 去重，同对象跨桶时退化平方；cell=96 密集桶 k 激增 | `core.js:55`、`game.js:2715` | 3000 敌密集时退化 |
| **5** | **每帧数组全量重建**：`filter` 重建 monsters/bullets + 每怪 3× `enemyTargets` new 数组 | `game.js:3035`、`3062-3063`、`1517-1518` | ~9000 数组/帧 + 8 长数组 |
| **6** | `nearestMonster` **全表扫**（反弹子弹触发） | `game.js:1843` | 多反弹时 O(B×M) 尖峰 |
| 7 | 敌人 AI 索敌 O(3M×H) | `1737/1748/1770` | 45k 距离/帧（尚可） |

**碰撞检测好消息**：子弹↔敌人**已有空间哈希** `monsterHash.query(x,y,30)`（`game.js:1572-1593`），**不是** O(B×M)；爆炸 AOE 与陷阱也走 hash（`1939-1952`、`3047`）。→ 2000×3000 的恐怖算式不成立，实际是 O(B×邻域)。

**对象池现状**：**全库无实体对象池**，仅 `_tmpArr`（`game.js:1841`）一个 scratch 数组复用属正确范式。
每帧新增对象粗算 **>2 万/帧**（常态）：敌弹命中 `aliveHeroes()` 新数组（`1277/1595`）≥2000、索敌 `enemyTargets` ~9000、粒子 `FX.parts` 峰值数万（`3264-3270`）、掉落 6000（`2001-2005`）。

**存档安全**：击杀写盘有 `!monsters[defId]` 守卫（`game.js:444`），**不会**每杀一怪写盘 ✅

**已有护栏**：PerfGuard（`main.js:50-102`，仅告警不降级）、isLowQuality 全套（`game.js:4703/4726`、剔除/粒子×0.4/网格×2/跳描边）、`CFG.monsterCap`（26.x 起按关卡分档 120→160→220→300，旧口径为全程 120）、`boss.bulletBudget:40`。

**测试可扩展性**：`perf_test.js` 已有 World 桩 + `testPoolVsNew` GC 压测（`perf_test.js:257-343/442`），扩规模只需改 `monsterCount` 常量。

## 三、架构方案（五条主线）

### 主线 A：渲染层（首崩点，收益最大）

| 措施 | 做法 | 预期 |
|---|---|---|
| **A1 视锥剔除常态化** | 把低画质的 `lqCull` 剔除提升为**全画质默认**（`3578-3580` 的 margin 逻辑解耦出 `isLowQuality` 条件） | 视野仅占地图 25~45% → 立即省 55~75% 绘制 |
| **A2 群体抽象 LOD** | 按「距相机距离 / 屏幕占比」分 3 档：<br>• **近档**（≤N 个阈值，如 60）：完整精灵 + 血条 + 受击闪白<br>• **中档**：精灵**无血条**、无 save/restore、共享 `globalAlpha`<br>• **远档**：**单次 `fillRect` 色点**（不 drawImage、不 beginPath）——同色点可合并批量绘制 | 3000 敌实际 drawImage 数降到 60~200 |
| **A3 弹幕批量绘制** | 同色同半径子弹**合并为一条 Path**（一次 `beginPath` + N 个 `arc` + 单次 `fill`）；或改 `fillRect` 方块弹（视觉可调） | 2000 弹从 2000 次 fill → 数十次 |
| **A4 消除 `ctx.filter`** | 受击闪白改「预生成 1 张闪白精灵」或 `globalCompositeOperation` 叠加，避免滤镜整层重绘（`3600`） | 去掉最贵状态 |
| **A5 血条预算** | 血条只给「近档 + 已受伤」敌人；受击短暂显示 | 省 3000×2 fillRect |

### 主线 B：空间分区（碰撞与查询）

| 措施 | 做法 |
|---|---|
| **B1 修 `query` 去重 O(k²)** | `core.js:55` 的 `indexOf` 去重改为**帧内查询序号标记**（每个对象存 `_qFrame`，命中即比对帧号）→ O(k) |
| **B2 自适应 cell 尺寸** | cell 从固定 96 改为按「敌人密度 / 数量」动态缩放（3000 敌时增大 cell，避免单桶候选爆炸） |
| **B3 分层网格** | 小怪群单独一张粗网格（远档只用于「是否被 AOE 覆盖」判定），精英/Boss 用细网格 |

### 主线 C：对象池与 GC（消除每帧分配）

| 优先级 | 对象 | 做法 |
|---|---|---|
| **P0** | `aliveHeroes()` / `enemyTargets` 每帧新数组（`1277/1517-1518`） | 复用模块级 scratch 数组（仿 `_tmpArr` 范式） |
| **P0** | 粒子 `FX.parts` / 飘字 `FX.floats`（`3263-3278`，峰值数万） | 真对象池：预分配 + 空闲链表 + `alive` 标记 |
| **P1** | `Bullet`（含 `new Set()` 的 hitSet） | 池化 + `hitSet.clear()` 复用 |
| **P1** | `Monster`（33 字段 + `ak` 18 字段） | 池化 + `ak` 按「怪物类型」缓存（同类型共享） |
| **P1** | `spawnPickup` 掉落（清屏 6000/帧） | 池化；或「合并掉落」（相邻掉落合一，附带省渲染） |
| **P2** | `filter` 重建长数组（`3035/3062-3063`） | 原地**末尾交换删除**（swap-remove）无需新数组 |
| **P2** | `explode` 的 `new Set()`（`1947`） | 模块级复用 |

### 主线 D：分级降配（两端兼顾）

- **D1 画质档位**：`低 / 中 / 高` 三档显式配置（扩展现有 `isLowQuality` 单开关为 `qualityLevel: 0|1|2`）
- **D2 敌人上限分级**：低档 800 / 中档 1500 / 高档 3000（`CFG.perf.tierCap`）
- **D3 降级触发**：PerfGuard 从「仅告警」升级为**自动降档**（连续 N 帧超阈值 → 降一档，冷却期不回升；提供手动覆盖）
- **D4 手机/电脑默认档**：按 `deviceMemory` / 分辨率 / UA 初始化默认档，用户可在设置里覆盖

### 主线 E：验证与压测（分阶段）

- **E1 独立压测场景**：不进正式关卡，加一个 `?stress=3000` 直达的场景（复用 `perf_test.js` 的 World 桩思路），可调敌人数/弹幕数/移动模式
- **E2 真机数据采集**：复用 PerfGuard 采样 + 新增「峰值帧耗时 / drawImage 计数 / 存活实体数」埋点，输出可读报告
- **E3 分阶段验收门槛**：
  - 阶段 1：逻辑层 3000+2000（无渲染）跑通、帧耗时 < 8ms
  - 阶段 2：渲染层 500 敌满精灵不掉帧
  - 阶段 3：1000 → 2000 → 3000 阶梯验收，每级手机+电脑双端
  - 阶段 4：接入正式玩法（载体待定）
